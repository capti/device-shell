# План: сайт учёта тестовых телефонов (qa-test-staff)

**Статус:** справочник и история решений; первоначальный MVP реализован.
Это не список текущих задач. Источник требований — OpenSpec
(`openspec/specs/`), любые изменения поведения — только через `openspec/changes/`.

Документ сохраняет первоначальный план, решения и детали проекта. Некоторые
разделы ниже исторические и могут не совпадать с реализацией; при расхождении
приоритет у OpenSpec и кода. Перед использованием старого пункта как задачи
сверьте его с `openspec/specs/<capability>/spec.md` и активными change.

---

## 1. Назначение

Сайт для учёта тестовых смартфонов, который отвечает на два вопроса по каждому
тестовому смартфону:

1. **За кем он закреплён** (владелец — постоянный ответственный).
2. **У кого он сейчас на руках** (держатель — тот, кто физически пользуется).

Дополнительно: история выдач, отчёты о состоянии устройства, фото, просроченные
возвраты, экспорт для менеджмента, уведомления администратору о значимых
действиях.

## 2. Стек и архитектура

```
┌──────────────────────┐   /api/* (dev)    ┌────────────────────────┐
│ Vite 8 + React + TS  │ ────────────────► │ FastAPI (Python 3.12)  │
│ Mantine, TanStack Q. │ ◄──────────────── │ :8000                  │
└──────────────────────┘   JSON + cookie   └───────────┬────────────┘
                                                       │
                                     ┌─────────────────┴──────────────┐
                                     │ SQLite (WAL) + data/media/     │
                                     └────────────────────────────────┘
```

- **Frontend:** Vite 8, React, TypeScript, React Router, TanStack Query,
  Mantine (таблицы, формы, модалки, даты).
- **Backend:** FastAPI, SQLAlchemy 2.0, Alembic (миграции с первого дня),
  Pydantic v2, `uv`, Argon2, `openpyxl`, `Pillow`.
- **БД:** SQLite в режиме WAL, файл `data/qa.db`.
- **Auth:** серверные сессии в БД + httpOnly cookie (не JWT — проще отзыв сессии).
- **Локальный запуск:** backend на `:8000`, frontend dev-сервер Vite на
  `:5173`; `dev.ps1` запускает оба процесса одной командой, оба с горячей
  перезагрузкой.
- **Production:** FastAPI обслуживает API и `/media/*`, но не SPA. Сборка
  `frontend/dist` раздаётся статическим сервером; reverse proxy с HTTPS
  направляет API и `/media/*` в FastAPI и поддерживает fallback SPA-маршрутов.
- В dev Vite проксирует запросы `/api/*` в FastAPI, снимая префикс.

## 3. Термины и роли

| Термин | Где живёт | Смысл |
|---|---|---|
| **admin** | `users.role` | глава тестеров + администратор сайта. Права на всё, включая управление пользователями |
| **user** | `users.role` | обычный тестировщик |
| **owner (владелец)** | `devices.owner_id`, NOT NULL | за кем телефон закреплён, кто отвечает за сохранность. Всегда ровно один, сменяемый |
| **holder (держатель)** | активная запись в `checkouts` | у кого телефон физически сейчас |
| **роль** | `users.role` | только право доступа к сайту. `owner`/`holder` — НЕ роли, а отношения к конкретному устройству |

Один человек одновременно может быть admin, владельцем трёх телефонов и
держателем одного чужого — поэтому это разные поля, а не одно `role`.

## 4. Модель данных

### users
```
id, username (UNIQUE), password_hash, full_name, email, team,
role ('admin' | 'user'), is_active (bool), created_at, last_login_at
```

### devices
```
id, inventory_no (UNIQUE), serial_no, imei, brand, model,
os, os_version, storage, color,
owner_id → users.id          NOT NULL
status ('active' | 'repair' | 'lost')
notes, archived_at (NULL = активен),
created_by → users.id, created_at, updated_at
```

### checkouts — история выдач, append-only
```
id, device_id, user_id (holder),
taken_at, expected_return_at, returned_at (NULL = активная),
condition_out, condition_in, comment_out, comment_in,
closed_reason ('returned' | 'transferred' | 'ownership_transferred'),
created_by → users.id
```
Partial unique index: `UNIQUE(device_id) WHERE returned_at IS NULL`.

### condition_reports — отчёты о состоянии
```
id, device_id, checkout_id (NULL), author_id → users.id,
condition ('ok' | 'scratches' | 'damaged' | 'not_working'),
requires_repair (bool), comment, created_at
```

### repairs — журнал ремонтов
```
id, device_id, sent_at, returned_at (NULL = в ремонте),
service, description, cost, comment, created_by → users.id
```

### device_photos
```
id, device_id, report_id (NULL), file_path, thumb_path,
uploaded_by → users.id, created_at
```

### device_events — аудит/таймлайн, append-only
```
id, device_id, actor_id, type, payload (JSON), created_at
```
Типы: `created`, `updated`, `owner_changed`, `checked_out`, `returned`,
`transferred`, `ownership_transferred`, `archived`, `restored`,
`status_changed`, `condition_reported`, `photo_added`, `photo_removed`.

### notifications
```
id, recipient_id → users.id, actor_id (NULL), type,
device_id (NULL), payload (JSON), read_at (NULL), created_at
index: (recipient_id, read_at)
```

### sessions
```
id, user_id, token_hash, created_at, expires_at, last_seen_at, user_agent
```

## 5. Ограничения (жёсткие правила)

Проверяются в сервисном слое; где возможно — дублируются в БД.

1. **Один владелец.** `owner_id` обязателен, всегда ровно один, сменяемый.
2. **Одна активная выдача.** Не более одной записи `checkouts` с
   `returned_at IS NULL` на устройство (partial unique index).
3. **Нельзя выдать самому себе.** При создании выдачи `holder != owner`.
4. **Передача владения текущему держателю** автоматически закрывает активную
   выдачу с `closed_reason = ownership_transferred`.
5. **Архив только без выдачи.** `POST /devices/{id}/archive` → `409
   ACTIVE_CHECKOUT`, если есть незакрытая выдача. Правило действует и для админа.
6. **Архив обратим.** Восстановление сохраняет владельца, спрашивает целевой
   статус (по умолчанию `active`).
7. **Смена владельца:** доступна текущему владельцу или админу. Если менял
   не админ — уведомление всем админам.
8. **Держатель самостоятелен:** может оставить отчёт о состоянии и вернуть
   телефон без участия владельца.
9. **Флаг `requires_repair` статус не меняет.** Перевод в `repair`/`lost` —
   только владелец или админ.
10. **Деактивация пользователя:** все устройства, которыми он владеет,
    автоматически уходят в архив. Если у него на руках чужие телефоны или у его
    устройств есть активные выдачи — деактивация отклоняется (`409`), сначала
    возврат/передача.
11. **Каждая мутация пишет `device_events`** в той же транзакции.
12. **Нет физического удаления.** Устройства — только в архив; пользователи —
    только деактивация.
13. **Просрочка** = активная выдача И `holder != owner` И
    `expected_return_at < today`. Одна функция на бэке для списка, дашборда,
    фильтров и Excel.
14. **Нельзя выдать** устройство в статусе `repair`/`lost` или в архиве.
15. **Архивное устройство read-only** — доступно только восстановление.
16. **Восстановление устройства, чей владелец деактивирован,** требует назначить
    нового владельца.

## 7. Вычисляемое состояние

```
active_checkout = checkout where returned_at IS NULL
holder          = active_checkout.user_id ?? device.owner_id
overdue         = active_checkout is not None
                  and active_checkout.user_id != device.owner_id
                  and active_checkout.expected_return_at < today
```

| Условие | Что показываем |
|---|---|
| `archived_at != NULL` | **В архиве** (серый) |
| `status = lost` | Утерян |
| `status = repair` | В ремонте |
| активная выдача + overdue | **Выдан · просрочен** (красный) |
| активная выдача | Выдан · у {holder} |
| иначе | У владельца · {owner} |

Состояния «на складе» нет: бесхозных телефонов не бывает.

Счётчики дашборда: всего активных / у владельцев / выдано / в ремонте /
утеряно / в архиве / просрочено.

## 8. API (первоначальный план; сверяйте с OpenSpec и реализацией)

| Группа | Эндпоинты |
|---|---|
| Auth | `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`, `POST /auth/change-password` |
| Devices | `GET /devices` (search, status, holder, overdue, mine, sort, page), `POST`, `GET /{id}`, `PATCH /{id}` |
| Владение | `POST /{id}/owner`, `POST /{id}/archive`, `POST /{id}/restore` |
| Оборот | `POST /{id}/checkout`, `POST /{id}/return`, `POST /{id}/transfer` |
| Статус | `POST /{id}/status` |
| Состояние | `GET /{id}/condition-reports`, `POST /{id}/condition-reports` |
| История | `GET /{id}/history` (events + checkouts + reports) |
| Фото | `POST /{id}/photos`, `DELETE /photos/{pid}`, раздача `/media/*` |
| Люди | `GET /users`, `GET /users/{id}`; admin: `POST/PATCH /users` |
| Уведомления | `GET /notifications`, `POST /notifications/{id}/read`, `POST /notifications/read-all` |
| Отчёты | `GET /reports/holders`, `GET /reports/overdue`, `GET /reports/export.xlsx`, `GET /dashboard/stats`, `GET /dashboard/charts` |

Коды ошибок: `409 ACTIVE_CHECKOUT` (архив при выдаче), `409 SELF_CHECKOUT`,
`409 HAS_DEVICES` (деактивация пользователя), `403` при нарушении матрицы прав.

## 9. Экраны и UX (актуальные маршруты SPA)

1. **/login** — форма входа.
2. **/dashboard** — счётчики, блок «Просроченные возвраты», графики и быстрый
   поиск.
3. **/devices** — таблица: инв. №, модель, статус, «Владелец», «На руках у»,
   дата возврата. Серверный поиск с debounce (модель/serial/IMEI/инв. №),
   фильтры-чипы, вкладка «Мои» (где я владелец + что держу), сортировка, пагинация.
4. **/devices/new** — форма; обычному пользователю владелец = он сам автоматически.
5. **/devices/:id** и **/devices/:id/edit** — карточка и редактирование:
   фото-галерея, характеристики, владелец (+ передать),
   держатель (+ выдать / принять / передать), статус, таймлайн истории,
   отчёты о состоянии, заметки. Кнопка «В архив» неактивна при активной выдаче
   с подсказкой «Сначала примите телефон у держателя».
6. **/people** — справочник сотрудников и управление ими для admin.
7. Уведомления доступны из колокольчика в шапке; отдельного маршрута
   `/notifications` в SPA нет.
8. **/reports** — сводка «у кого что», просрочки и выгрузка Excel.
9. **/me** — устройства пользователя и смена пароля.

Интерфейс на русском. Модалки выдачи/возврата требуют выбора состояния;
фото — drag&drop, до 5 на устройство.

### Сценарий возврата держателем
1. Карточка → «Вернуть».
2. Модалка: состояние (ок / царапины / повреждён / не работает), комментарий,
   чекбокс «требует ремонта», до 5 фото.
3. Отправка → выдача закрывается, отчёт сохраняется, телефон снова у владельца.
4. Владелец видит в таймлайне и получает уведомление.

Отдельная кнопка **«Сообщить о состоянии»** — тот же отчёт без возврата.

## 10. Уведомления

In-app: колокольчик со счётчиком и список уведомлений в интерфейсе.
Polling TanStack Query раз в 30–60 с (без WebSocket — достаточно для локального
хостинга).

| Событие | Получатель |
|---|---|
| Смена владельца не-админом | все admin |
| Архив / восстановление не-админом | все admin |
| Статус «утерян» / флаг «требует ремонта» | все admin |
| Возврат телефона | владелец |
| Новый отчёт о состоянии | владелец |

## 11. Фото, экспорт, бэкапы

- Фото: `data/media/devices/{device_id}/`, превью через Pillow, лимит размера,
  форматы jpeg/png/webp.
- Экспорт: `.xlsx` через openpyxl, учитывает текущие фильтры и содержит листы
  «Все устройства», «Просроченные», «История выдач». На листах устройств
  производитель выведен отдельной колонкой перед моделью.
- Бэкап: скрипт копирует `data/qa.db` + `data/media/` с датой в имени; запуск
  вручную или по планировщику Windows. Без бэкапа media история состояния
  теряется.

## 13. Этапы первоначальной реализации (завершены)

Этот раздел — историческая оценка объёма, а не актуальный план работ.

### Этап 1. Каркас + БД + авторизация — выполнен
- Инициализация backend/frontend, Alembic, первая миграция со всеми таблицами.
- Сессии, логин/логаут, `/auth/me`, защита роутов, роли, первый админ через CLI.
- Проверка прав по матрице + тесты на отказы.
- **Готово, когда:** вход по паролю работает, без сессии — 401.

### Этап 2. Устройства: CRUD + список + карточка — выполнен
- API и формы, серверный поиск/фильтры, вкладка «Мои».
- Таблица и карточка (без оборота), архив/восстановление.
- **Готово, когда:** 10 телефонов заводятся, ищутся, редактируются,
  архивируются и возвращаются из архива.

### Этап 3. Владение и оборот + история — выполнен
- Смена владельца, checkout, return, transfer, статусы, проверка инвариантов.
- Автозакрытие выдачи при передаче владения держателю, запрет self-checkout.
- Таймлайн, вычисляемые holder/overdue.
- **Готово, когда:** выдача → видна у человека → возврат → осталась в истории;
  архив при активной выдаче даёт 409.

### Этап 4. Люди, дашборд, просрочки, уведомления — выполнен
- `/users`, `/users/{id}`, статистика, графики, список просроченных.
- Таблица notifications, API, колокольчик и список уведомлений.
- **Готово, когда:** просрочка подсвечивается только при `holder != owner`;
  смена владельца не-админом приходит админу.

### Этап 5. Фото, отчёты о состоянии, Excel — выполнен
- Загрузка/удаление фото, превью, привязка к отчётам.
- Отчёт о состоянии, возврат с фиксацией состояния.
- Экспорт `.xlsx` с фильтрами и листом просрочек.
- **Готово, когда:** фото видно в карточке, Excel совпадает с экраном.

### Этап 6. Полировка, тесты, локальный запуск — выполнен
- Pytest на инварианты и права, README, `dev.ps1`, скрипт бэкапа, `.env.example`.
- **Готово, когда:** на чистой машине backend и Vite запускаются отдельными
  процессами, бэкап создаётся.

## 14. Первоначальные допущения

- Интерфейс только на русском; часовой пояс — локальный серверный.
- Email/Telegram-рассылок нет, уведомления только в интерфейсе.
- Импорт существующего парка из Excel/CSV не нужен — заводим руками.
- Роль `viewer` не вводится: все аутентифицированные пользователи могут
  смотреть всё.
- Vite 8 и Mantine фиксируются по актуальной версии на этапе 1.
- Один сервер, один экземпляр приложения, SQLite достаточен для команды.

### S. Приёмка MVP
1. Создал телефон → он числится за мной.
2. Выдал коллеге → в карточке holder, в списке «Выдан · у …».
3. Просрочка подсвечена только при `holder != owner`.
4. Коллега вернул → отчёт о состоянии, телефон у владельца, владелец получил уведомление.
5. Архив во время выдачи → 409 и понятное сообщение.
6. Обычный пользователь сменил владельца → у всех админов уведомление.
7. Excel совпадает с экраном с учётом фильтров.
8. Пользователь не может редактировать чужое устройство (403 + тест).

### T. Что не входит в MVP
Учёт SIM-карт, гарантия, QR-коды, Telegram/email, CSV-импорт, PWA,
интеграции с Jira/TestRail, мультиязычность, SSO, мобильное приложение,
инвентаризация-сверка, массовое переназначение при увольнении.
