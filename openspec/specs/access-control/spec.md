# access-control Specification

## Purpose
Определяет, кто может войти в систему и какие действия с устройствами и
пользователями ему разрешены.

## Requirements

### Requirement: Вход по паролю

Система SHALL аутентифицировать пользователя по username и паролю и отклонять
вход при неверных учётных данных.

#### Scenario: Успешный вход
- **WHEN** пользователь отправляет верные username и пароль
- **THEN** система устанавливает сессионную cookie и возвращает профиль пользователя

#### Scenario: Неверный пароль
- **WHEN** пользователь отправляет неверный пароль
- **THEN** система отвечает 401 и не устанавливает сессию

### Requirement: Серверная сессия

После входа система SHALL выдавать httpOnly cookie с идентификатором серверной
сессии и MUST отклонять запросы без действующей сессии.

#### Scenario: Запрос без сессии
- **WHEN** клиент вызывает защищённый эндпоинт без cookie
- **THEN** система отвечает 401

#### Scenario: Недействительная сессия
- **WHEN** клиент присылает cookie с истёкшей или отозванной сессией
- **THEN** система отвечает 401 и требует повторный вход

### Requirement: Срок жизни сессии

Сессия SHALL действовать 7 дней от последней активности пользователя.

#### Scenario: Продление при активности
- **WHEN** пользователь работает на шестой день после входа
- **THEN** срок сессии продлевается ещё на 7 дней

#### Scenario: Истечение после простоя
- **WHEN** с последней активности прошло больше 7 дней
- **THEN** система считает сессию недействительной и отвечает 401

### Requirement: Роль admin

Пользователь с ролью admin SHALL управлять любыми устройствами и справочником
пользователей.

#### Scenario: Админ редактирует чужое устройство
- **WHEN** admin сохраняет изменения устройства, которым не владеет
- **THEN** система применяет изменения

#### Scenario: Админ создаёт пользователя
- **WHEN** admin создаёт нового пользователя
- **THEN** система создаёт учётную запись с указанной ролью

### Requirement: Роль user

Пользователь с ролью user SHALL управлять только устройствами, которыми владеет,
и теми, что у него на руках, и MUST NOT управлять справочником пользователей.

#### Scenario: Пользователь редактирует своё устройство
- **WHEN** user сохраняет изменения устройства, которым владеет
- **THEN** система применяет изменения

#### Scenario: Пользователь редактирует чужое устройство
- **WHEN** user пытается изменить устройство, которым не владеет и которое не держит
- **THEN** система отвечает 403

#### Scenario: Пользователь управляет справочником
- **WHEN** user пытается создать или изменить пользователя
- **THEN** система отвечает 403

### Requirement: Права держателя

Держатель чужого устройства SHALL возвращать его и оставлять отчёт о состоянии
без участия владельца.

#### Scenario: Возврат чужого устройства
- **WHEN** holder нажимает «Вернуть» на устройстве, которым владеет другой человек
- **THEN** система закрывает выдачу и фиксирует состояние

### Requirement: Ограничение попыток входа

Система SHALL разрешать не более 5 неудачных попыток входа в минуту и
блокировать дальнейшие попытки на 15 минут.

#### Scenario: Превышение лимита
- **WHEN** с одного адреса поступает шестая неудачная попытка за минуту
- **THEN** система отвечает 429 и не проверяет пароль

### Requirement: Защита последнего администратора

Система MUST NOT позволять разжаловать или деактивировать последнего активного
пользователя с ролью admin.

#### Scenario: Попытка разжаловать последнего админа
- **WHEN** admin пытается сменить роль последнего активного admin на user
- **THEN** система отвечает 409 и сохраняет роль

### Requirement: Смена собственного пароля

Пользователь SHALL менять собственный пароль после подтверждения текущего.
После успешной смены система SHALL отзывать все остальные сессии пользователя,
сохраняя сессию, которой подтверждена смена пароля.

#### Scenario: Успешная смена пароля

- **WHEN** пользователь вводит верный текущий пароль и новый пароль от 8 символов
- **THEN** система сохраняет новый хеш пароля

#### Scenario: Отзыв остальных сессий после смены пароля

- **WHEN** пользователь успешно меняет свой пароль, имея несколько сессий
- **THEN** текущая сессия остаётся действительной, а все остальные сессии
  пользователя отклоняются при следующем запросе

#### Scenario: Слишком короткий пароль

- **WHEN** новый пароль короче 8 символов
- **THEN** система отвечает 422 и не меняет пароль или сессии

### Requirement: Проверка Origin на мутациях

Система SHALL отклонять мутирующие запросы, у которых заголовок Origin не
совпадает с адресом приложения, и MUST отклонять мутации без Origin в
production. В dev и test запросы без Origin SHALL пропускаться.

#### Scenario: Запрос с чужим Origin
- **WHEN** POST-запрос приходит с Origin другого сайта
- **THEN** система отвечает 403 и не выполняет изменение

#### Scenario: Мутация без Origin в production
- **WHEN** POST-запрос приходит без Origin, а приложение работает в production
- **THEN** система отвечает 403 и не выполняет изменение

#### Scenario: Мутация без Origin в dev
- **WHEN** POST-запрос приходит без Origin в dev или test
- **THEN** система выполняет изменение
