# audit-log Specification

## Purpose
Сохраняет полную историю изменений устройств и входов, чтобы можно было
разобраться, кто и когда что сделал.

## Requirements

### Requirement: События устройства

Каждая мутация устройства SHALL создавать событие с типом, автором, временем и
полезной нагрузкой.

#### Scenario: Создание устройства
- **WHEN** пользователь создаёт устройство
- **THEN** в истории появляется событие `created` с автором

#### Scenario: Ошибка во время записи события
- **WHEN** запись события не удалась
- **THEN** вся операция откатывается и изменение не сохраняется

### Requirement: Таймлайн устройства

Карточка устройства SHALL показывать все события в обратном хронологическом
порядке.

#### Scenario: Просмотр истории
- **WHEN** пользователь открывает карточку устройства
- **THEN** он видит события от новых к старым с автором и временем

### Requirement: Глобальный журнал

Admin SHALL видеть журнал событий всех устройств с фильтрами по дате и
устройству через `GET /audit/events`. Журнал SHALL отдавать события от новых к
старым с номером устройства (`inventory_no`), автором, типом, русской подписью
типа и полезной нагрузкой.

Если не заданы ни устройство, ни диапазон дат, журнал SHALL ограничивать
выборку последними 30 днями. Границы диапазона дат SHALL считаться
включительно: `from_at` — с начала дня, `to_at` — до конца дня в локальном
времени сервера.

#### Scenario: Фильтр по дате
- **WHEN** admin задаёт диапазон дат
- **THEN** журнал содержит только события внутри диапазона

#### Scenario: Границы диапазона включительно
- **WHEN** admin задаёт диапазон с `from_at` и `to_at` внутри одной даты
- **THEN** в журнал попадают события этого дня с 00:00:00 до 23:59:59

#### Scenario: Фильтр по устройству
- **WHEN** admin выбирает конкретное устройство
- **THEN** журнал содержит только его события

#### Scenario: Окно по умолчанию
- **WHEN** admin запрашивает журнал без фильтров
- **THEN** в журнал попадают события за последние 30 дней, а более старые —
  нет

#### Scenario: Порядок и состав события
- **WHEN** admin запрашивает журнал
- **THEN** события идут от новых к старым и содержат номер устройства, автора,
  тип, подпись типа и полезную нагрузку

#### Scenario: Журнал только для администратора
- **WHEN** пользователь с ролью `user` запрашивает журнал
- **THEN** система отвечает 403 `FORBIDDEN` и не возвращает события

### Requirement: Журнал входов

Система SHALL фиксировать каждую попытку входа — успешную и неуспешную — со
временем, введённым логином, исходом, причиной отказа, IP-адресом и
user-agent. Записи журнала SHALL быть неизменяемыми на уровне базы данных.

Admin SHALL видеть журнал через `GET /audit/logins` с фильтрами по дате,
логину и исходу. Количество записей в ответе SHALL ограничиваться, чтобы поток
неудачных попыток не раздувал ответ.

#### Scenario: Неуспешный вход

- **WHEN** пользователь вводит неверный пароль
- **THEN** в журнале появляется запись с исходом «неуспешно» и причиной
  «неверные учётные данные»

#### Scenario: Успешный вход

- **WHEN** пользователь входит с верным паролем
- **THEN** в журнале появляется запись с исходом «успешно» и ссылкой на
  пользователя

#### Scenario: Попытка с неизвестным логином

- **WHEN** вход пытаются выполнить под логином, которого нет
- **THEN** в журнале появляется запись с введённым логином и без ссылки на
  пользователя

#### Scenario: Попытка под деактивированной учётной записью

- **WHEN** вход пытаются выполнить под деактивированной учётной записью
- **THEN** в журнале появляется неуспешная запись с причиной
  «деактивированная учётная запись»

#### Scenario: Попытка, отсечённая rate-limit'ом

- **WHEN** вход отклонён ограничителем попыток
- **THEN** в журнале появляется неуспешная запись с причиной «rate limit»
  и введённым логином

#### Scenario: Отказ базы данных не прячет попытку

- **WHEN** вход отклонён с кодом 401 или 429
- **THEN** запись журнала сохраняется, несмотря на откат транзакции запроса

#### Scenario: Запись нельзя изменить или удалить

- **WHEN** кто-либо пытается изменить или удалить запись журнала
- **THEN** база данных отклоняет операцию

#### Scenario: Фильтры и ограничение ответа

- **WHEN** admin запрашивает журнал с фильтрами по дате, логину и исходу
- **THEN** ответ содержит только подходящие записи, не больше заданного
  лимита, и общее число подходящих записей

#### Scenario: Журнал входов только для администратора

- **WHEN** пользователь с ролью `user` запрашивает журнал входов
- **THEN** система отвечает 403 `FORBIDDEN` и не возвращает записи

### Requirement: Бессрочное хранение истории

Система MUST NOT удалять или изменять записи истории и аудита. Запрет SHALL
действовать на уровне базы данных, а не только через отсутствие эндпоинтов.

#### Scenario: Попытка очистки истории
- **WHEN** кто-либо пытается удалить событие
- **THEN** база данных отклоняет операцию

#### Scenario: Попытка изменить событие
- **WHEN** кто-либо пытается изменить существующее событие
- **THEN** база данных отклоняет операцию

#### Scenario: Штатная запись события
- **WHEN** приложение добавляет новое событие
- **THEN** событие сохраняется, а прежние записи остаются неизменными
