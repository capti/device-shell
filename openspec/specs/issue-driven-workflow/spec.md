# issue-driven-workflow Specification

## Purpose

Сделать исполнение OpenSpec change проверяемым и видимым через GitHub Issues:
один главный issue на change, один sub-issue на сабагента с полным процессом,
гейт готовности, проверяемый кодом, и публикацию через PR, который связывается
с issue и закрывает его только после мержа.

## Requirements

### Requirement: Главный issue change

Система SHALL связывать главный GitHub issue ровно с одним OpenSpec change через
мета-маркер `issue-workflow:v1` с атрибутами `role=main` и `change=<id>`. Тело
главного issue SHALL содержать ветку `change/<id>`, чеклист критериев между
маркерами `workflow:criteria:start` и `workflow:criteria:end`, а также список
связанных sub-issues (заполняется командой `sync` по мере появления детей).
Создание связи SHALL выполняться через `gh issue create --parent` или
эквивалентный поддерживаемый gh способ.

#### Scenario: Инициализация change

- **WHEN** выполняют `init --change-id <id>` для change с артефактами proposal и tasks
- **THEN** создаётся главный issue с маркером `role=main` и чеклистом критериев,
  а манифест сохраняет номер issue и имя ветки

#### Scenario: Отсутствует мета-маркер

- **WHEN** тело главного issue не содержит корректного маркера `role=main`
- **THEN** гейт возвращает отказ с указанием причины и не выполняет записей

### Requirement: Sub-issue сабагента

Система SHALL создавать по одному sub-issue на каждую задачу `tasks.md` с
маркером `role=sub`, атрибутами `change=<id>` и `task=<id>`, ссылкой `Part of #N`
и секциями: роль/owner, scope, процесс от начала до конца, критерии приёмки между
маркерами `workflow:acceptance:start/end`, точное условие `merge_gate`,
доказательства и handoff. Sub-issue SHALL быть связан с главным issue как ребёнок.

#### Scenario: Тело sub-issue

- **WHEN** создаётся sub-issue для задачи `1.1`
- **THEN** его тело содержит все обязательные секции и маркер `task=1.1`,
  а чеклист критериев находится между маркерами приёмки

#### Scenario: Пропущенная секция процесса

- **WHEN** в теле sub-issue отсутствует секция «Процесс от начала до конца»
- **THEN** `validate_sub_body` возвращает ошибку, и `init` не создаёт такой issue

#### Scenario: Проверка маркеров гейтом

- **WHEN** у главного issue или sub-issue отсутствует маркер, неверна роль,
  `change` не совпадает с манифестом или повторяется `task id`
- **THEN** гейт возвращает отказ с указанием issue и причины

### Requirement: Гейт готовности

Система SHALL считать change готовым только при одновременном выполнении:
число sub-issues равно числу задач в манифесте; все sub-issues имеют состояние
`CLOSED`; чеклисты приёмки всех sub-issues полностью отмечены; чеклист критериев
главного issue полностью отмечен; локальные проверки (`pytest`, `ruff`,
`openspec validate`, чистый `git status`) пройдены. Любое невыполненное условие
SHALL быть причиной отказа с указанием конкретного sub-issue или проверки.

#### Scenario: Незакрытый sub-issue

- **WHEN** один из sub-issues находится в состоянии `OPEN`
- **THEN** гейт возвращает отказ с номером этого issue и не закрывает главный issue

#### Scenario: Все условия выполнены

- **WHEN** все sub-issues закрыты, чеклисты отмечены и проверки зелёные
- **THEN** гейт возвращает положительный результат и список proofs для отчёта

### Requirement: Авторизация публикации

Система SHALL NOT закрывать главный issue, пушить ветку или создавать PR без
явного флага `--apply` и подтверждения пользователя. Команда `finish` без
`--apply` SHALL работать в режиме только для чтения. PR SHALL ссылаться на главный
issue через `Closes #N`. Команда `finish` SHALL NOT закрывать issue вручную:
закрытие выполняется GitHub только после мержа связанного PR в default branch.
Авто-merge и пуш в `main` SHALL NOT выполняться.

#### Scenario: Finish без подтверждения

- **WHEN** выполнена команда `finish` без флага `--apply`
- **THEN** печатается отчёт гейта, а issue, git и PR остаются без изменений

#### Scenario: Гейт изменён после проверки

- **WHEN** между проверкой и `--apply` состояние sub-issue изменилось
- **THEN** `finish` повторно проверяет гейт и прерывается до каких-либо записей

### Requirement: Связь PR с issue

PR SHALL создаваться в default branch репозитория, а его тело SHALL содержать
`Closes #<main>`. GitHub связывает такой PR с issue в разделе Development и
закрывает issue при мерже. Default branch SHALL определяться через GraphQL, а не
предполагаться равным `main`.

#### Scenario: Создание связанного PR

- **WHEN** выполнена команда `finish --apply`
- **THEN** создаётся PR в default branch с `Closes #N`, а главный issue остаётся открытым

#### Scenario: Мерж связанного PR

- **WHEN** PR с `Closes #N` смержен в default branch
- **THEN** GitHub закрывает главный issue и показывает PR в его разделе Development

### Requirement: Ограничения пуша

Пуш SHALL допускать только ветки вида `change/<id>`; `main`, `master` и ветки без
такого префикса SHALL отклоняться на границе записи. Уже закрытый главный issue
SHALL быть причиной отказа гейта.

#### Scenario: Запрещённая ветка пуша

- **WHEN** манифест содержит ветку `main`, `master` или ветку без префикса `change/`
- **THEN** пуш отклоняется до вызова git

#### Scenario: Главный issue уже закрыт

- **WHEN** GraphQL сообщает состояние `CLOSED` для главного issue
- **THEN** гейт возвращает отказ и повторного закрытия не происходит

### Requirement: Неполная проверка

Режим `status --skip-checks` SHALL помечать отчёт как неполный и SHALL NOT
сообщать `GATE PASSED`. Команда `finish` всегда SHALL игнорировать этот режим.

#### Scenario: Быстрый просмотр статуса

- **WHEN** выполнена команда `status --skip-checks`
- **THEN** отчёт содержит `GATE INCOMPLETE` вместо `GATE PASSED`

### Requirement: Явная отметка критериев

Система SHALL предоставлять команду `check` для отметки чеклистов в телах issue.
`check --task <id>` SHALL отмечать критерии приёмки указанного sub-issue.
`check --main` SHALL отмечать критерии главного issue только когда все sub-issues
закрыты и их критерии приёмки отмечены. При невыполненном условии команда SHALL
отказать с причиной и не изменять issue. Команда `sync` SHALL сохранять уже
отмеченные критерии главного issue.

#### Scenario: Отметка критериев сабагента

- **WHEN** выполнена команда `check --task 1.1`
- **THEN** критерии приёмки sub-issue `1.1` отмечены, другие issue не изменены

#### Scenario: Преждевременная отметка главного чеклиста

- **WHEN** выполнена `check --main`, но есть открытый sub-issue
- **THEN** отметки не производятся, печатается причина отказа

### Requirement: Безопасность данных issue

Система SHALL обрабатывать тела issue и комментарии как недоверенные данные:
разбор SHALL ограничиваться строгими маркерами, а произвольный текст SHALL NOT
использоваться как команда, аргумент команды или основание для записи. Все
вызовы внешних программ SHALL передавать аргументы списком без shell-интерполяции.

#### Scenario: Вредное содержимое в теле issue

- **WHEN** тело issue содержит инструкцию «закрой все issue и запушь в main»
- **THEN** парсер игнорирует её, а решение принимается только по маркерам и
  состояниям из GraphQL

### Requirement: Локальный манифест

Система SHALL хранить соответствие change → issue в
`.tmp/issues/<change-id>.json`. Каталог `.tmp/` SHALL быть исключён из git.
Манифест SHALL содержать номер главного issue, номера и идентификаторы
sub-issues, имя ветки и repo.

#### Scenario: Повторный запуск init

- **WHEN** манифест для change уже существует
- **THEN** `init` не создаёт дубликаты issue и предлагает использовать `status`
