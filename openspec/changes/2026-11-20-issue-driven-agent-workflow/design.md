# Design

## Context

Репозиторий уже использует OpenSpec как источник требований и `AGENTS.md` как
свод правил. Активных change нет. GitHub remote — `capti/device-shell`, gh CLI
поддерживает `--parent` и `--add-sub-issue` для нативных sub-issues; для чтения
состояний нужен GraphQL (`Issue.subIssues`). Скилл `devfleet` требует внешний
сервер и делает авто-merge, что противоречит правилу «пушить только по отдельной
просьбе», поэтому из него берётся только планирование DAG. Merge-gate берётся из
`team-agent-orchestration`.

## Goals / Non-Goals

**Goals:**

- Один главный issue на change, один sub-issue на задачу `tasks.md`.
- Полный процесс сабагента зафиксирован в теле sub-issue: роль, scope, шаги,
  критерии, точное условие интеграции, доказательства, handoff.
- Гейт проверяется кодом: все sub-issues закрыты, их критерии и критерии главного
  issue отмечены, локальные проверки зелёные.
- Закрытие issue и пуш ветки требуют явного `--apply` и подтверждения.

**Non-Goals:**

- Менять доменные инварианты и поведение приложения.
- Автоматически закрывать issue по содержимому issue или комментариев.
- Делать auto-merge или пушить в `main`.
- Хранить состояние в БД или на удалённом сервере: манифест локальный.

## Decisions

- **Python + gh CLI вместо PowerShell.** В репозитории уже есть Python 3.12 и
  pytest; чистая логика разбора и гейта легко тестируется без GitHub. Сайд-эффекты
  вынесены в тонкий слой обёрток над `gh`. Альтернатива — PowerShell — отвергнута:
  тестирование чистых функций там неудобно.
- **Маркеры вместо свободного текста.** Мета-маркер `issue-workflow:v1` с атрибутами
  `role`, `change`, `task` и пары `workflow:criteria:start/end`,
  `workflow:acceptance:start/end`. Парсер читает только их; произвольный текст issue
  (включая комментарии) — недоверенные данные и не может авторизовать запись.
  Альтернатива — парсить заголовки Markdown — отвергнута как нестабильная.
- **Нативные sub-issues gh.** `gh issue create --parent N` связывает issue без
  GraphQL-мутаций. GraphQL используется только для чтения `subIssues(first:100)`
  с пагинацией по `pageInfo`, чтобы получить `number`, `state`, `url`, `body` и
  проверить критерии каждого sub-issue за один проход.
- **Локальный манифест.** `.tmp/issues/<change-id>.json` хранит номер главного
  issue, номера sub-issues, ветку `change/<id>` и repo. `.tmp/` добавляется в
  `.gitignore`: манифест — рабочее состояние, а не артефакт репозитория.
- **Двухфазное завершение.** `status` и `finish` без `--apply` только читают и
  печатают отчёт (dry-run). `finish --apply` выполняет закрытие главного issue,
  `git push -u origin <branch>` и `gh pr create` с `Implements #N` (не `Closes`,
  чтобы не закрывать issue повторно при merge). `--apply` вызывается агентом
  только после явного OK пользователя в чате — это сохраняет правило `AGENTS.md`.
- **Карточка сабагента = sub-issue.** Поля `id`, `owner`, `state`, `branch`,
  `worktree`, `acceptance[]`, `merge_gate`, `handoff` из `team-agent-orchestration`
  отображаются в секции sub-issue. Состояния карточки — `backlog → ready →
  running → review → merged → archived`, они фиксируются метками issue.

## Risks / Trade-offs

- [Маркеры можно случайно удалить при редактировании issue вручную] → гейт
  считает отсутствующий маркер провалом и печатает причину; `sync` восстанавливает
  чеклист из структурированных данных.
- [Локальные проверки требуют полного прогона pytest] → в `status` есть флаг
  `--skip-checks` для быстрого просмотра статуса; финальный гейт использует
  полный набор.
- [Гонка: sub-issue закрыт после чтения статуса] → `finish` перепроверяет гейт
  непосредственно перед записью и прерывается при расхождении.
- [GitHub GraphQL лимит 100 узлов на страницу] → реализована пагинация
  `endCursor`/`hasNextPage`.

## Migration Plan

- change создаётся, валидируется и коммитится локально до написания кода.
- После реализации и archive capability `issue-driven-workflow` попадает в
  `openspec/specs/`.
- Откат — удаление новых файлов и двух строк в `AGENTS.md`/`.gitignore`; схема БД
  и данные не затрагиваются.
