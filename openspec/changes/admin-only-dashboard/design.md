# Design

## Context

- Бэкенд: `GET /dashboard/stats` и `GET /dashboard/charts` в
  `backend/app/api/reports.py` сейчас зависят от `get_current_user` — роль
  не проверяется. Зависимость `require_admin` в `backend/app/api/deps.py`
  уже существует (403 `FORBIDDEN`, «Недостаточно прав») и применяется в
  `users.py` / `audit.py`.
- Фронтенд: `ProtectedLayout` в `frontend/src/routes.tsx` уже загружает
  `me()` (роль в `data.role`) и рендерит `AppShellFrame` — но не проверяет
  роль. `NAV_ITEMS` в `AppShell.tsx` статичен. `LoginPage` после входа
  идёт на `from` или на `/dashboard`; catch-all `*` ведёт на `/dashboard`.
- Фронтенд-тестов нет, только `tsc -b`, `vite build`, `oxlint`. Бэкенд
  покрывается `pytest` (хелперы `register_user(role=...)`, `login_as`).

## Goals / Non-Goals

**Goals:**

- Роль user не видит дашборд: нет пункта меню, редирект с `/dashboard`,
  403 от API (страховка).
- Один источник правды по роли на фронте — `me()` в `ProtectedLayout`.

**Non-Goals:**

- `/reports` и Excel-экспорт — доступны всем аутентифицированным.
- Изменение состава счётчиков, графиков, формулы просрочки.
- Редиректы для неавторизованных (остаются как есть, на `/login`).

## Decisions

### D1. Проверка роли на бэкенде — `Depends(require_admin)` на двух роутах

Заменить `get_current_user` на `require_admin` в `read_dashboard` и
`read_dashboard_charts` (`backend/app/api/reports.py`).

- **Почему не в сервисе**: проверка роли — валидация на границе (boundary),
  роуты тонкие, сервис `reports.py` остаётся чистым и протестируемым без HTTP.
- **Порядок ошибок**: `require_admin` = `get_current_user` + проверка роли,
  поэтому без сессии — 401, с ролью user — 403. Существующий тест
  `test_reports_require_authentication` продолжает проходить.
- **Альтернатива (отклонена)**: собственная зависимость «admin-or-403» —
  дублировала бы уже существующий `require_admin`.

### D2. Гард маршрута — в `ProtectedLayout`, до рендера страницы

После успешного `me()`: если `location.pathname === '/dashboard'` и
`data.role !== 'admin'` → `<Navigate to="/devices" replace />`.

- **Одно решение — одно место**: покрывает все пути на `/dashboard`:
  прямой URL, catch-all `*` → `/dashboard`, и пост-логин редирект
  (`LoginPage` всегда ведёт на `from` или `/dashboard` — менять её не нужно,
  итоговый URL для user будет `/devices`).
- **Дашборд не монтируется**: `DashboardPage` не рендерится, запросы
  `dashboard-stats` / `dashboard-charts` не уходят.
- **Попутно бесплатно**: при смене роли в открытой сессии рефетч `me()`
  обновит `data`, и гард сам уведёт демотированного админа с `/dashboard`.
- **Альтернативы (отклонены)**: обёртка `RequireRole` вокруг маршрута —
  больше кода для единственного случая; проверка внутри `DashboardPage` —
  страница уже смонтирована и запросы ушли; отдельный редирект в `*` —
  не покрыл бы прямой URL и `from=/dashboard`.

### D3. Пункт меню — флаг `adminOnly` + фильтр в `AppShellFrame`

Добавить `{ label: 'Дашборд', to: '/dashboard', adminOnly: true }` в
`NAV_ITEMS` и рендерить `NAV_ITEMS.filter((item) =>
!item.adminOnly || user.role === 'admin')`.

- `user` уже передаётся в `AppShellFrame` — новая передача данных не нужна.
- **Альтернатива (отклонена)**: два массива `NAV_ITEMS` на роль — дублирование
  списка и расхождение пунктов при правках.

### D4. Ошибки API на фронте — без новых механизмов

Гард не даёт странице монтироваться для user, поэтому 403 с `/dashboard/*`
— страховка (прямой fetch, изменившаяся роль между рендерами). Конверт
`{code, message}` уже показывается тостом существующим обработчиком
ошибок (`Недостаточно прав`), отдельная ветка не нужна.

## Risks / Trade-offs

- [Кэш TanStack Query: уходящий со страницы user мог получить данные до
  demote] → роли в кэше не хранятся, `me()` — единственный источник; после
  рефетча гард уводит с маршрута, а `queryClient.clear()` при выходе сбрасывает
  кэш.
- [Кто-то из user полагается на `/dashboard` как на стартовую страницу
  (закладка)] → редирект на `/devices` ведёт на основной рабочий раздел,
  поведение согласовано со спекой.
- [Сценарии «Вход с корректными данными» и навигации в спеках уточнены под
  роль] → дельты в change покрывают это явно, архивация обновит основные спеки.

## Migration Plan

Деплой один процесс (FastAPI + `frontend/dist`), миграций БД нет.

1. Бэкенд и фронтенд меняются в одном коммите — рассинхрон возможен только
   при выкатке частями: старый фронт + новый бэк → у user на `/dashboard`
   тост «Недостаточно прав» (корректно деградирует, данные не утекают).
2. Откат — обычный `git revert`, состояние БД не менялось.
