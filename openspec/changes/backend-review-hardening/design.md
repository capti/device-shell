# Design

## Context

Текущее состояние зафиксировано в `proposal.md`. Ключевые ограничения:
локальный процесс FastAPI с единственным воркером uvicorn; SQLite в режиме WAL;
схема меняется только Alembic-миграциями; бизнес-логика по `AGENTS.md` живёт в
`backend/app/services/`. Спеки `device-photos` и `audit-log` задают наблюдаемое
поведение, которое сохраняется; меняются только условия отказа и порядок.

## Goals / Non-Goals

**Goals:**

- Отклонять перегруженные и «бомбовые» загрузки фото до выделения больших
  объёмов памяти и до обращения к БД за правами.
- Убрать полное сканирование из глобального журнала, дашборда и истории
  экспорта за счёт индексов по датам.
- Обеспечить стабильный порядок журнала при равном времени.
- Вернуть роуты в соответствие с правилом «тонкий роут, БД только в сервисах»
  без изменения отклонений и ответов.

**Non-Goals:**

- Менять доменные инварианты, коды ошибок и формат успешных ответов.
- Внедрять глобальный middleware ограничения размера тела для всех эндпоинтов.
- Менять срок жизни сессий, cookie, пул соединений и `busy_timeout`.
- Рефакторить схемы валидации, аннотации типов и форматирование всего проекта.

## Decisions

- **Проверка фото до чтения.** Размер каждой части и всей пачки проверяется по
  метаданным `UploadFile` до вызова `.read()`; права (`ensure_can_act_on_hold`)
  и состояние устройства проверяются в сервисе до чтения файлов; число файлов
  в запросе ограничено на уровне роута. Альтернатива — оставить проверку в
  `_decode()` после `.read()` — отклонена: к моменту проверки память уже
  выделена, а неавторизованный запрос всё равно расходует ресурсы.
- **Защита от декомпрессионных бомб.** Явно задаётся предел числа пикселей,
  `Image.open()` ограничивается списком поддерживаемых форматов, габариты
  проверяются до `image.load()`, а `DecompressionBombError` и
  `DecompressionBombWarning` трактуются как `UNSUPPORTED_FORMAT` (422).
  Альтернатива — полагаться на стандартный `MAX_IMAGE_PIXELS` — отклонена:
  он допускает предупреждение в интервале 89–178 Мп, чего достаточно для
  выделения сотен мегабайт.
- **Индексы, а не переписывание запросов.** Добавляются
  `ix_device_events_created_at`, `ix_checkouts_taken_at_id` и
  `ix_checkouts_returned_at`. Существующий `(device_id, created_at)` сохраняется
  для таймлайна устройства. Композитный `(taken_at, id)` покрывает и фильтр
  дат, и сортировку истории `ORDER BY taken_at DESC, id DESC`. Альтернатива —
  агрегировать в SQL или кэшировать — отклонена как более рискованная при
  текущем объёме данных.
- **Детерминированный порядок.** В глобальный запрос журнала добавляется
  `id.desc()` как второй ключ сортировки — так же, как уже сделано в
  таймлайне, списке фото и уведомлениях. Это устраняет нестабильность при
  секундной точности `clock.now_local()`.
- **Перенос логики в сервисы.** Обновление `last_login_at`, поиск фото по id и
  построение/выполнение запроса глобального журнала переносятся в существующие
  сервисы по образцу `services/lookup.py` и `services/login_audit.py`. Роут
  остаётся тонким: вызов сервиса + валидация ответа Pydantic-схемой.
- **Тонкая обёртка прав доступа (3.4).** Задача предлагала заменить локальный
  `_require_admin` общим `require_admin` напрямую, но общая зависимость выдаёт
  сообщение «Недостаточно прав», а контракт журнала фиксирует «Доступ к журналу
  аудита только для администраторов». Сохранена синхронная типизированная
  обёртка: решение о праве принимает `require_admin`, обёртка только
  переопределяет текст ответа 403 `FORBIDDEN`. Прямая замена изменила бы формат
  ответа, что исключено из объёма изменения.

## Risks / Trade-offs

- [Жёсткий предел пикселей может отклонить корректное, но очень детализированное
  фото] → предел выбирается с запасом и проверяется тестом на граничном
  изображении; значение не фиксируется в спеке и может быть подстроено без
  изменения требований.
- [Индексы увеличивают объём БД и стоимость записи] → таблицы истории и выдач
  пополняются редко, а выигрыш на чтении критичен; индексы добавляются без
  перестроения данных.
- [Перенос кода в сервисы может случайно изменить поведение] → изменения
  покрываются существующими API-тестами, отдельный тест проверяет, что ответы
  и коды ошибок не изменились.

## Migration Plan

- Новая Alembic-ревизия создаёт три индекса; `downgrade()` удаляет только их.
- Миграция не трогает данные и не меняет семантику существующих индексов,
  включая partial unique index активной выдачи.
- Порядок выкладки: сначала код, затем миграция; откат кода не требует
  отката миграции, откат миграции безопасен и обратим.
- Проверка: `uv run alembic upgrade head`, `uv run alembic check` и тесты
  миграций на temp-БД.
