# backend-backup Specification

## Purpose

Операционная обвязка B9: бэкап через планировщик Windows и живой `/health` с
проверкой БД. Журнал аудита живёт в спеке `audit-log` (изменение
`audit-log-endpoint`), структурные логи — в спеке `structured-logging`: этот
change их только проверяет, новых требований не добавляет.

## ADDED Requirements

### Requirement: `/health` с проверкой БД

`GET /health` SHALL возвращать не только статус приложения, но и результат
проверки доступности БД.

#### Scenario: БД жива

- **WHEN** запрос приходит к живой БД
- **THEN** ответ содержит `status: "ok"`, `version` и `database: "ok"`

#### Scenario: БД недоступна

- **WHEN** БД недоступна
- **THEN** ответ содержит `status: "degraded"` и `database: "error"`, код
  ответа — 503

### Requirement: Скрипт бэкапа

Система SHALL предоставлять `backup.ps1`, который создаёт резервную копию
базы и media без интерактивных запросов и завершается с кодом 0 при успехе.

#### Scenario: Запуск без параметров

- **WHEN** запускают `backup.ps1` из корня репозитория с работающей БД
- **THEN** создаётся каталог копии с базой и media, команда завершается с
  кодом 0

#### Scenario: Планировщик Windows

- **WHEN** Планировщик Windows запускает `backup.ps1` как задание
- **THEN** копия создаётся без интерактивных запросов и код выхода 0

#### Scenario: Лимит копий

- **WHEN** бэкап создаётся десятый раз при лимите 14
- **THEN** все копии сохраняются; при двадцать пятой копии удаляется самая
  старая, остаётся 14

#### Scenario: Повтор в ту же секунду

- **WHEN** бэкап запускают дважды в пределах одной секунды
- **THEN** второй раз команда завершается ошибкой и каталог не создаётся заново
