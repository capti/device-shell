# Design: backend-backup

## Общее

B9 — операционная часть: `/health` с проверкой БД, структурные логи (уже есть,
подтверждаем покрытие) и `backup.ps1` для планировщика. Бэкап уже реализован в
`services/backup.py` и `cli.py`; осталось только обёртка и проверка
планировщиком. Журнал аудита вынесен в отдельный change `audit-log-endpoint`
со спекой `audit-log`: требование о глобальном журнале уже есть в `audit-log`,
дублировать его в `backend-backup` нельзя.

## Backup

- `backup.ps1` — PowerShell-скрипт в корне репозитория, который вызывает
  `python -m app.cli backup --yes-style` без интерактивных запросов. В планировщике
  запускается из корня репозитория, поэтому `data/` и виртуальное окружение
  определяются относительно него.
- Копия создаётся в `data/backups/qa-backup-<дата>_<время>/`, база снимается через
  SQLite backup API (не копирование файла), media копируется целиком.
- Лимит 14 копий хранится в `KEEP_BACKUPS`, удаление старых происходит сразу после
  создания новой. Повтор в ту же секунду даёт `BACKUP_EXISTS`.

## Журнал аудита

Реализован в change `audit-log-endpoint`: `GET /audit/events` из `device_events`
с фильтрами по устройству и датам, только админ. Здесь остаётся только
ссылка — требование и его сценарии описаны в спеке `audit-log`.

Расхождение с первоначальной версией этого design закрыто в пользу реализации:
`device_id` — числовой идентификатор устройства, а не инвентарный номер;
запрос принимает ISO 8601, а не `ДД.ММ.ГГГГ`; поддержки wildcard `*` нет —
фильтр по умолчанию и так возвращает все устройства.

## `/health`

- `GET /health` пытается выполнить простой `SELECT 1` через `SessionLocal`.
- При успехе: `{status: "ok", version: "...", database: "ok"}`.
- При ошибке: `{status: "degraded", version: "...", database: "error"}`, 503.

## Структурные логи

- `logs.py` уже настроен на JSON-вывод с полями `method`, `path`, `status_code`,
  `duration_ms` через middleware `RequestLogMiddleware`.
- Секреты не передаются в лог: в middleware нет тела запроса, cookie, заголовков
  авторизации. Проверяем тестом на входе с паролем.
- Исключения ловит обработчик `Exception` в `errors.py`, пишет `exception` с
  трейсбеком и статусом 500.

### Покрытие требований `structured-logging`

Требование не новое — спека `structured-logging` уже действует, поэтому этот
change только сверяет её сценарии с тестами, ничего не добавляя:

| Сценарий спеки | Тест |
| --- | --- |
| Формат записи: одна JSON-строка с timestamp, level, logger, message и полями из `extra` | `test_formatter_writes_single_json_record`, `test_configure_logging_emits_json` |
| Кириллица не экранируется | `test_formatter_keeps_cyrillic_readable` |
| Уровень берётся из настройки | `test_configure_logging_respects_level` |
| Повторная настройка не дублирует вывод | `test_configure_logging_is_repeatable` |
| Успешный запрос: method, path, status_code, duration_ms | `test_request_is_logged_with_fields` |
| Отказ проверки Origin попадает в лог со статусом 403 | `test_origin_rejection_is_logged` |
| Необработанное исключение: ERROR, трейсбек, клиенту 500 | `test_unhandled_error_is_logged_with_traceback`, `test_formatter_keeps_traceback` |
| Пароль из тела входа не попадает в лог | `test_request_log_does_not_contain_secrets` |

После восстановления `OriginCheckMiddleware` в `main.py` все восемь тестов
проходят; отдельная работа по логам не потребовалась.

## Проверка бэкапа

- Тест на чистом `data/`: создать базу, запустить `backup.ps1`, проверить, что
  копия содержит `qa.db` и `media/`, содержимое совпадает с источником (база
  открывается, таблицы есть, медиа-файлы повторяют исходные).
- Тест через планировщик Windows: добавить задание, запустить его, проверить код
  выхода 0 и появление копии.
- Тест лимита: создать 15 копий с искусственными метками времени, проверить, что
  осталось 14 и самая старая удалена.
- Тест повтора в ту же секунду: создать копию, модифицировать время, попытаться
  создать ещё одну в ту же метку — ошибка `BACKUP_EXISTS`.
