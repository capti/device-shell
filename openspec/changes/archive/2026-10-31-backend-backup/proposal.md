# Proposal: backend-backup

## Why

Дальнейшие операционные шаги из плана: журнал аудита, `/health`, структурные
логи и скрипт бэкапа (`B9`), затем тесты на инварианты, OpenAPI и README
бэкенда (`B10`). Логи уже структурные (`structured-logging`), бэкап-сервис и
CLI-команды есть.

Делаю операционную часть за один OpenSpec change «backend-backup»: только то,
что лежит в B9. Журнал аудита (`/audit/events`) и `/health` с проверкой БД
уже реализованы; логи реализованы раньше и здесь только сверяются с
требованиями. Осталось проверить бэкап через планировщик Windows.

## What Changes

Закрыть B9 в одном изменении `backend-backup`, состоящем из:

1. **Backup** — реализовано (`services/backup.py`, `cli.py`) вместе с
   `backup.ps1`; проверено на лимите 14 копий, повторе в ту же секунду и
   содержимом копии.
2. **Журнал аудита** — вынесен в отдельный change `audit-log-endpoint`: спека
   `audit-log` уже содержит требование «Глобальный журнал», и дублировать его
   в `backend-backup` нельзя. Реализация: `GET /audit/events`, фильтры по
   устройству и датам, только админ.
3. **`/health` с проверкой БД** — реализовано и покрыто тестами
   (`tests/test_health.py`): `database: "ok"|"error"`, 503 при недоступности.
4. **Структурные логи** — требование живёт в спеке `structured-logging`;
   здесь только сверка сценариев с тестами, новых требований не добавляем.

Мелкие задачи с HU < 1/2 дня и без новых требований не выношу отдельным
change — внутри этого.
