# Design

## Context

- Модели `Device`, `Checkout`, `ConditionReport`, `Repair`, `DeviceEvent`
  существуют с первой миграцией; partial unique index
  `uq_checkouts_active_device` гарантирует не более одной активной выдачи.
  Миграции не нужны.
- `device_state.py` уже вычисляет `holder_id` и `overdue` одним SQL-выражением
  и умеет писать события без коммита (`record_event`). Формулу просрочки
  повторять нельзя.
- `devices.py` содержит `ensure_can_manage` (admin или владелец),
  `get_device`, `has_active_checkout`.
- Ошибки — `AppError(code, message, status)`; ответы устройства —
  `DeviceRead` с `owner`, `holder`, `overdue`, `expected_return_at`.
- Тесты работают через `TestClient` и реальный `POST /auth/login`, схема
  поднимается `Base.metadata.create_all`.

## Goals / Non-Goals

**Goals:**

- Все переходы оборота — по одному HTTP-вызову, в одной транзакции с событием
  истории.
- Права проверяются в сервисах, роуты тонкие.
- Ошибки с кодами, которые фронт показывает пользователю без перевода.
- Держатель и просрочка после каждой мутации совпадают с формулой
  `device_state`.

**Non-Goals:**

- Уведомления (B6), фото (B8), Excel (B7), управление пользователями (B5).
- Пакетные операции, отмена выдачи «как будто не было», редактирование
  закрытых выдач.
- Изменение схемы БД.

## Decisions

### 1. Разделение сервисов по смыслу

| Модуль | Ответственность |
|---|---|
| `services/checkouts.py` | выдача, возврат, передача держателю, история выдач, общие проверки держателя |
| `services/ownership.py` | смена владельца и автозакрытие выдачи |
| `services/maintenance.py` | статусы `lost`/`active`, журнал ремонтов |
| `services/condition_reports.py` | отчёты о состоянии |

`checkouts.py` и `ownership.py` создают отчёт о состоянии через
`condition_reports.create_report(...)`, а активную выдачу ищут через
`device_state.active_checkout(db, device_id)`. Так нет циклических импортов и
одно место, где определяется «активная выдача».

### 2. Матрица прав

| Операция | Кто |
|---|---|
| смена владельца, выдача, архив/восстановление, ремонт, статус | владелец или admin |
| возврат, передача держателю | текущий держатель, владелец или admin |
| отчёт о состоянии | текущий держатель, владелец или admin |
| чтение выдач, отчётов, ремонтов, истории | любой авторизованный |

Проверки:

- `ensure_can_manage(device, actor)` — владелец или admin (уже есть);
- `ensure_can_act_on_hold(db, device, actor)` — admin, владелец или активный
  держатель; иначе `403 FORBIDDEN`.

### 3. Выдача

`POST /devices/{id}/checkout` принимает `holder_id`, `expected_return_at`,
`condition_out`, `comment_out`.

Порядок проверок задаёт коды ошибок:

1. устройство не найдено — `404 DEVICE_NOT_FOUND` (общий `get_device`);
2. архивное — `409 DEVICE_ARCHIVED`;
3. `status != active` — `409 DEVICE_UNAVAILABLE`;
4. уже есть активная выдача — `409 ALREADY_CHECKED_OUT`;
5. держатель = владелец — `409 SELF_CHECKOUT`;
6. держатель не найден или деактивирован — `422 HOLDER_INACTIVE`;
7. дата возврата раньше сегодняшней полуночи — `422`.

Дата по умолчанию — `now_local() + 14 дней` (P1, C2). Пустая дата в API не
создаёт бессрочную выдачу; формула `overdue` всё равно защищена от `NULL`
(требование «бессрочная выдача»), потому что строки могут появиться из
будущих операций и из данных.

Дата трактуется как дата (полночь), поэтому «сегодня» ещё не просрочка:
`overdue` сравнивает `expected_return_at < today_start()`.

### 4. Закрытие выдачи — одна функция

`_close(checkout, reason, condition_in, comment_in)` выставляет `returned_at`,
`closed_reason`, `condition_in`, `comment_in`. Причины:

- `returned` — держатель вернул или владелец закрыл забытую выдачу;
- `transferred` — передача другому держателю;
- `ownership_transferred` — новый владелец стал текущим держателем.

`returned_at` и `closed_reason` всегда выставляются вместе — это проверяет
check-constraint БД.

### 5. Возврат

`POST /devices/{id}/return` требует `condition_in` (одно из `ok`,
`scratches`, `damaged`, `not_working`) и необязательные `comment_in`,
`requires_repair`. Отчёт о состоянии создаётся в той же транзакции и
привязывается к закрываемой выдаче (требование `condition-reports`), событие
`condition_reported` пишется вместе с `returned`. Флаг `requires_repair` не
меняет `devices.status` — ремонт оформляется отдельной операцией.

Активной выдачи нет — `409 NO_ACTIVE_CHECKOUT`.

### 6. Передача между держателями

`POST /devices/{id}/transfer` требует `holder_id` нового держателя. В одной
транзакции: старая выдача закрывается (`transferred`, при указании состояния
создаётся отчёт), новая открывается на нового держателя с
`condition_out = condition_in`, датой по умолчанию +14 дней и
`created_by = actor`.

Передача самому владельцу запрещена (`409 SELF_CHECKOUT`): вернуть телефон
владельцу — это `/return`, иначе возникла бы активная выдача с
`holder == owner`, ломающая инвариант 3. Передача текущему держателю —
`409 SAME_HOLDER`.

### 7. Смена владельца

`POST /devices/{id}/owner` с `owner_id`:

- новый владелец деактивирован или не найден — `422 OWNER_INACTIVE`;
- тот же владелец — идемпотентный no-op без события;
- архивное устройство — `409 DEVICE_ARCHIVED` (read-only);
- активная выдача и новый владелец = её держатель → выдача закрывается с
  `ownership_transferred`, пишутся события `owner_changed` и
  `checkout_closed`;
- иначе держатель не меняется (требование «передача при активной выдаче»).

### 8. Статусы и ремонт

`repair` меняется только через журнал:

- `POST /devices/{id}/repairs` — владелец/admin, нет активной выдачи (иначе
  `409 ACTIVE_CHECKOUT`), статус `active` (иначе `409 DEVICE_UNAVAILABLE`);
  создаёт запись `repairs` с `sent_at`, ставит `status = repair`, событие
  `repair_started`.
- `POST /devices/{id}/repairs/{repair_id}/finish` — владелец/admin; запись
  должна принадлежать устройству и быть открытой (`404 REPAIR_NOT_FOUND`,
  `409 REPAIR_ALREADY_FINISHED`); заполняет `returned_at` (по умолчанию
  сейчас) и `comment`, возвращает `status = active`, событие
  `repair_finished`.

`lost` и возврат из `lost` — `POST /devices/{id}/status`:

- `lost` только из `active` (иначе `409 INVALID_STATUS_TRANSITION`), событие
  `status_changed`; активная выдача не мешает — телефон мог потерять держатель;
- `active` только из `lost`, непустой `comment` обязателен
  (`422 COMMENT_REQUIRED`, C7), комментарий попадает в событие;
- архивное устройство — `409 DEVICE_ARCHIVED`.

### 9. Отчёты о состоянии

`POST /devices/{id}/condition-reports` принимает `condition`,
`requires_repair`, `comment`. Отчёт привязывается к активной выдаче, если она
есть, иначе `checkout_id = NULL` (владелец фиксирует состояние без выдачи).
Недопустимое значение — 422 от Pydantic, посторонний — `403 FORBIDDEN`.
Список отдаётся от новых к старым.

### 10. События и транзакции

Каждая операция: мутация → `record_event` → один `db.commit()`. Ошибка на
любом шаге откатывает всё, включая событие (`audit-log`). Payload содержит
только идентификаторы и значимые значения, чтобы таймлайн был читаемым.

| Событие | Когда |
|---|---|
| `checked_out` | создана выдача |
| `returned` | выдача закрыта возвратом |
| `transferred` | передача другому держателю |
| `checkout_closed` | автозакрытие при передаче владения |
| `owner_changed` | смена владельца |
| `condition_reported` | новый отчёт о состоянии |
| `repair_started` / `repair_finished` | журнал ремонтов |
| `status_changed` | `active` ↔ `lost` |

### 11. Формат ответов

Мутации возвращают `DeviceRead` — фронт сразу видит нового держателя,
владельца и `overdue` без второго запроса. Журналы (`/checkouts`,
`/repairs`, `/condition-reports`) отдают списки с автором/связанной выдачей.
Выдача в API (`CheckoutRead`) содержит `id`, `device_id`, `holder`,
`taken_at`, `expected_return_at`, `returned_at`, `closed_reason`,
`condition_out/in`, `comment_out/in`, `created_by`.

### 12. Тестируемость

Каждая ручка проверяется через HTTP с реальными сессиями. Отдельные тесты на
инварианты: self-checkout, одна активная выдача, автозакрытие при передаче
владения держателю, запрет архива/ремонта при активной выдаче, просрочка
только при `holder != owner`, обязательный комментарий при возврате из
`lost`. Состояние в карточке после мутации сверяется с `GET /devices` — одна
формула.

## Risks / Trade-offs

- **Уведомления отложены до B6** → спеки `notifications` временно не
  выполнены; триггеры добавятся в тех же сервисах, контракты ручек не
  изменятся.
- **Дата возврата хранится как `datetime`** → фронт присылает дату, она
  нормализуется в полночь; сравнение с `today_start()` не даёт ложной
  просрочки в день возврата.
- **Передача владельцу через `/owner` при активной выдаче** → держатель
  остаётся прежним, это явно описано тестом.
- **`/status` не умеет `repair`** → ремонт всегда имеет запись журнала; это
  осознанное ужесточение, чтобы не появлялось `repair` без истории.
- **Много кодов ошибок** → фронт показывает `message`, код используется для
  ветвлений; все коды перечислены в README.

## Migration Plan

Миграций нет. Перезапуск backend и `uv run python -m app.export_openapi`.
Откат — revert коммита; данные не меняются.
