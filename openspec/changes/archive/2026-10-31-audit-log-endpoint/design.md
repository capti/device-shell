# Design

## Context

События уже пишутся: каждая мутация устройства создаёт запись в `device_events`
(`type`, `actor_id`, `payload`, `created_at` c индексом
`ix_device_events_device_created`), а таймлайн одного устройства отдаёт
`GET /devices/{id}/history`. Открытых вопросов по хранению нет — меняется
только способ чтения: вместо истории одного устройства нужен срез по всем.

## Decisions

1. **Один read-only запрос с `outerjoin` к `devices`.** Для события нужно
   `inventory_no`, а само устройство удаляется только в архив, поэтому join
   безопасен; `outerjoin` — на случай события, чьё устройство недоступно.
   Роут тонкий: построение запроса и разбор строк — в `app/api/audit.py`,
   отдельный сервис не нужен — это чтение без бизнес-правил.

   Выборка читается через `execute(query).all()` без `.unique()`: `payload` —
   JSON, и SQLAlchemy отказывается применять стратегию уникальности к строке с
   нехешируемым значением. `.unique()` нужен только для joined-eager-load
   коллекций, здесь его нет.

2. **Границы диапазона раскрываются до дня, включительно.** `from_at` →
   `00:00:00.000000`, `to_at` → `23:59:59.999999`, в локальном времени
   сервера (`app/clock.now_local`), как и в остальных датах проекта. Иначе
   выбранный в календаре последний день обрезался бы на время создания
   первого события.

3. **Окно 30 дней по умолчанию, только когда нет ни device_id, ни дат.**
   Запрос без параметров — типичный первый запрос журнала; без окна он
   вернул бы всю историю и лёг на индекс линейным сканом. Если фильтры
   заданы — окно не подмешивается, иначе старые события молча исчезали бы.

4. **Диапазон с `from_at > to_at` не ошибка.** Такой запрос вернёт пустой
   список: валидация границ — зона UI, а 422 на «левом» фильтре из curl
   усложняет клиент без выигрыша.

5. **Админ-проверка через `Depends` и `AppError`, как в других
   admin-эндпоинтах.** Ответ 403 уходит через существующий обработчик в формате
   `{code, message}`, без отдельного middleware и без ролей в БД.

6. **Русские подписи типов событий — константой в модуле роута.** Словарь
   типов закрыт (`created`, `checked_out`, `returned` и т.д.); для
   неизвестного типа отдаётся сам код, чтобы новый тип не ломал ответ.

## Risks / Trade-offs

- **Нет пагинации.** За 30 дней на QA-команде событий немного, а фильтры
  сужают выборку. Пагинация добавится, если журнал начнут дергать без фильтров
  на длинной истории.
- **Список типов дублируется с фронтендом** (таймлайн показывает подписи).
  Дубль терпим: оба места читают один словарь-источник только для отображения.
- **`actor_id` без имени.** Имя пользователя — отдельный запрос; для админа,
  разбирающего инцидент, id достаточно, а карточка пользователя открывается по
  нему. Усложнение с join'ом к `users` откладывается до frontend-изменения.

## Migration Plan

Нет: эндпоинт только читает существующие данные, схема БД не меняется,
фронтенд его не вызывает до отдельного change.

## Alternatives Considered

- **Отдельный сервис `app/services/audit.py`** — отклонён: чистое чтение с
  фильтрами без правил и побочных эффектов дало бы слой-обёртку вокруг одного
  `select`.
- **Обязательные `from_at`/`to_at`** — отклонён: противоречило бы спеке,
  которая говорит о фильтрах как об опциях, и сделало бы первый запрос
  журнала невозможным.
- **`GET /devices/history` без device_id** — отклонён: путь с переменной
  `{id}` не позволяет обойтись без неё, а отдельный префикс `/audit/`
  сохраняет пространство имён под журнал входов.
