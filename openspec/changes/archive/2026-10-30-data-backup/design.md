# Design

## Context

`data/` содержит `qa.db` (SQLite в режиме WAL) и `media/` с фотографиями.
Каталог целиком в `.gitignore`, поэтому потеря диска означает потерю всей
учётной информации и фото. Общие требования — G3 (ежедневно, 14 копий), R1
(бэкап перед обновлением), R2 (скрипт восстановления и инструкция), R5 (ручная
проверка восстановления раз в квартал).

Существующие паттерны: бизнес-логика в `backend/app/services/`, CLI в
`backend/app/cli.py`, ошибки — `AppError(code, message, status)`, путь данных —
`settings.data_dir`.

## Goals / Non-Goals

**Goals:**

- Одна команда снимает согласованную копию базы и media.
- Копии не растут бесконечно: держим 14 последних.
- Данные можно вернуть из копии без ручного копирования файлов.
- Копирование запускается планировщиком без интерактивных запросов.

**Non-Goals:**

- API, миграции и изменения существующих инвариантов.
- Шифрование и выгрузка копий за пределы машины.
- Проверка целостности копий по расписанию.

## Decisions

1. **Логика в `app/services/backup.py`, CLI — тонкая оболочка.**
   Команды `backup` и `restore` в `cli.py` только парсят аргументы, печатают
   результат и превращают `AppError` в код возврата 1. Так же устроен
   `create-admin`.

2. **Копия базы через `sqlite3.Connection.backup`, а не `shutil.copy2`.**
   В WAL-режиме часть закоммиченных страниц лежит в `-wal`; копирование одного
   файла даёт устаревшую базу. Backup API читает данные через соединение и
   пишет целостный снимок. Зависимостей не добавляет — это stdlib.
   Альтернатива: `VACUUM INTO` — отклонена, требует места в той же директории и
   не даёт контроля над именем файла в копии.

3. **Каталог копии: `data/backups/qa-backup-<ГГГГ-ММ-ДД>_<ЧЧ-ММ-СС>`,**
   внутри `qa.db` и `media/`. Имя с меткой времени сортируется
   лексикографически, поэтому ретенция — это `sorted(...)[:-keep]` без чтения
   метаданных файлов. Секундная точность достаточна для ежедневного запуска;
   повторный запуск в ту же секунду отвечает `BACKUP_EXISTS`, а не затирает
   предыдущую копию.

4. **Атомарность на уровне каталога**: копия пишется в целевой каталог, при
   любом исключении он удаляется целиком (`rmtree`), чтобы не оставлять
   полупустых копий. Аналогично устроена компенсация в загрузке фото.

5. **Ретенция после успешного копирования, `keep` по умолчанию 14 (G3).**
   Ограничение проверяется до любых удалений: `--keep 0` отвечает
   `BACKUP_KEEP_INVALID` и ничего не трогает.

6. **Восстановление**: база перезаписывается тем же backup API, затем `media`
   заменяется целиком. Файл базы не подменяется на диске — на Windows это
   может упереться в открытый дескриптор. Каталог без `qa.db` считается
   некорректной копией (`BACKUP_INVALID`), данные при этом не меняются.
   Восстановление выполняется при остановленном uvicorn — это записано в README.

7. **`backup.ps1` повторяет стиль `dev.ps1`**: ищет `uv` в PATH, иначе
   запускает `python -m uv`, и не задаёт интерактивных вопросов.

8. **Настройка `backup_dir`** — свойство `Settings` (`data_dir / "backups"`).
   В `tests/conftest.py` каталог копий чистится перед каждым тестом вместе с
   media, чтобы копии не протекали между тестами.
