# Design

## Context

Проект стартует с нуля: кода нет, есть только `PLAN.md` с согласованными
требованиями и `AGENTS.md` с кратким контекстом. Спеки в `openspec/specs/`
пока отсутствуют. См. `proposal.md` — Why.

## Goals / Non-Goals

**Goals:**

- Разложить требования `PLAN.md` на 10 capability-спек с проверяемыми сценариями.
- Зафиксировать границы capability так, чтобы будущие changes не создавали
  дублирующих спек.
- Сделать baseline без кода, чтобы спеки стали основной правдой до первой
  миграции БД.

**Non-Goals:**

- Проектирование схемы БД, API-контрактов и структуры модулей — это следующий
  change `bootstrap-backend`.
- Описание визуального дизайна и фронтенд-архитектуры.
- Замена `PLAN.md`: он остаётся справочником и историей решений.

## Decisions

### 1. Десять capability-спек вместо одной общей

**Решение:** разделить поведение по устойчивым областям: `access-control`,
`device-inventory`, `device-ownership`, `checkout-lifecycle`,
`condition-reports`, `repair-journal`, `user-management`, `notifications`,
`reports-export`, `audit-log`.

**Почему:** каждая область меняется независимо. Смена правила просрочки
затрагивает `checkout-lifecycle` и `reports-export`, но не `user-management`.
Одна большая спека заставляла бы любой change переписывать сотни требований.

**Альтернативы:** одна спека `phone-tracking` — проще на старте, но дельты
становятся нечитаемыми; спека на каждый экран — привязывает требования к UI,
который ещё не спроектирован.

### 2. Термины и инварианты живут в контексте, а не дублируются в каждой спеке

**Решение:** определения `owner`, `holder`, роли и список инвариантов занесены в
`openspec/config.yaml`. В спеках они используются как данность, а проверяемое
поведение описано сценариями.

**Почему:** контекст подмешивается в каждый артефакт автоматически. Дублирование
определений в 10 файлах гарантирует расхождение при первом же изменении.

### 3. Baseline-изменение без кода

**Решение:** это изменение содержит только `proposal.md`, спеки, `design.md` и
`tasks.md`; после проверки оно архивируется, и дельты становятся основными
спеками.

**Почему:** OpenSpec требует, чтобы требования появлялись через change. Прямое
написание файлов в `openspec/specs/` обошло бы валидацию и историю.

### 4. Спеки описывают наблюдаемое поведение

**Решение:** в спеках нет имён классов, таблиц и эндпоинтов; есть входы,
результаты и коды ошибок (`409 ACTIVE_CHECKOUT`), которые видит клиент.

**Почему:** реализация может измениться без изменения контракта. Коды ошибок
включены, потому что на них опирается фронтенд и сценарии приёмки.

### 5. Просрочка описана в двух спеках явно

**Решение:** правило просрочки присутствует и в `checkout-lifecycle` (когда
наступает), и в `reports-export` (что отчёты используют то же правило).

**Почему:** это единственное требование, которое обязано совпадать в трёх местах
(список, дашборд, Excel). Явное дублирование контракта предотвращает расхождение
в реализации.

## Risks / Trade-offs

- **Расхождение `PLAN.md` и спек** → после архивации `PLAN.md` помечается как
  справочник; любые изменения поведения идут только через OpenSpec changes.
- **Спеки описывают ещё не существующее поведение** → это осознанно: baseline
  фиксирует целевое состояние, а `bootstrap-backend` и последующие changes
  закрывают разрыв. До реализации ни один change не считается выполненным.
- **Слишком крупные capability** → границы выбраны по изменяемости, а не по
  экранам; при росте `device-inventory` можно выделить `device-photos`.
- **Сценарии могут быть недостаточно конкретными** → каждый сценарий содержит
  проверяемый результат; при реализации он превращается в тест.

## Migration Plan

1. Проверить `openspec validate --all`.
2. Архивировать `define-requirements` — дельты попадут в `openspec/specs/`.
3. Обновить `AGENTS.md`: OpenSpec — канон, `PLAN.md` — справочник.
4. Создать `bootstrap-backend` для B0–B2.

## Покрытие инвариантов

| # | Инвариант | Где закреплён |
|---|---|---|
| 1 | Один обязательный владелец | `device-ownership` — «Единственный обязательный владелец» |
| 2 | Не более одной активной выдачи | `checkout-lifecycle` — «Одна активная выдача» |
| 3 | Запрет self-checkout | `checkout-lifecycle` — «Выдача устройства» |
| 4 | Передача владения держателю закрывает выдачу | `device-ownership` — «Передача владения текущему держателю» |
| 5 | Архив только без выдачи | `device-inventory` — «Архивация без активной выдачи» |
| 6 | Просрочка: holder ≠ owner и дата прошла | `checkout-lifecycle` — «Просрочка возврата»; `reports-export` — «Единое правило просрочки» |
| 7 | Нет физического удаления | `device-inventory` — «Запрет удаления устройства»; `user-management` — «Запрет удаления пользователя» |
| 8 | Деактивация архивирует устройства | `user-management` — «Деактивация пользователя»; «Блокировка деактивации при обороте»; `device-inventory` — «Восстановление из архива» |
| 9 | Мутация и событие в одной транзакции | `audit-log` — «События устройства» |
| 10 | Архивное устройство read-only | `device-inventory` — «Архивное устройство только для чтения» |
| 11 | Запрет выдачи repair/lost/архив | `checkout-lifecycle` — «Запрет выдачи недоступных устройств»; `repair-journal` — «Запрет оборота во время ремонта» |
| 12 | Защита последнего admin | `access-control` — «Защита последнего администратора» |
