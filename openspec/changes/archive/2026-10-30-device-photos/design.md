# Design

## Context

Таблица `device_photos` и модели `DevicePhoto` существуют с первой миграции,
`pillow` и `python-multipart` уже в зависимостях, но эндпоинтов и раздачи файлов
нет. Мотивация и границы — в `proposal.md` (Why / Не входит), требования — в
дельта-спеках `device-photos` и `condition-reports`.

Существующие паттерны, которые повторяем: тонкие роуты + сервисный слой
(`app/services/`), конверт ошибок `AppError(code, message, status)`,
`record_event` без коммита (коммитит вызывающий сервис), сериализаторы в
`app/api/serializers.py`.

## Goals / Non-Goals

**Goals:**

- Загрузка/чтение/удаление фото через API с валидацией на входе.
- Файлы на диске с превью, отдача `/media/*` без сессии.
- Одна транзакция на мутацию: строка `device_photos` + `device_events`.

**Non-Goals:**

- Фронтенд-галерея и модалки (следующий frontend-этап).
- Миграции БД, изменения существующих инвариантов, бэкап `data/media/`.

## Decisions

1. **Отдельный роутер `app/api/photos.py`** с префиксом `/devices`
   (`POST/GET /{id}/photos`) и без префикса (`DELETE /photos/{pid}`) — так
   разделено намерение и не раздувается `maintenance.py`, где уже 8 роутов.
   Альтернатива: добавить в `maintenance.py` — отклонена, файл и так выше
   остальных по размеру.

2. **Один multipart-загрузчик на запрос**: `files: list[UploadFile]` +
   `report_id: int | None = Form(None)`. Фронт шлёт пачку файлов одним
   запросом (до 5), бэкенд валидирует каждый и сохраняет атомарно: если хоть
   один файл невалиден — не сохраняется ни один (согласуется со сценарием
   «лишний файл не сохраняется»). Альтернатива: по одному файлу — отклонена,
   фронт пришлёт 5 запросов вместо одного.

3. **Валидация по содержимому, не по расширению**: размер читается первым
   (лимит 10 МБ — до любой декомпрессии), затем `Pillow.Image.open(...).verify()`
   и проверка `format in {JPEG, PNG, WEBP}`. Лимит 5 — счётчиком по
   `device_photos` устройства внутри сервиса, до записи файлов.
   Коды ошибок: `PHOTO_TOO_LARGE`, `UNSUPPORTED_FORMAT`, `PHOTO_LIMIT`,
   `REPORT_DEVICE_MISMATCH` — все с 422, чтобы фронт различал сообщения.

4. **Хранение**: `data/media/devices/{device_id}/{uuid4().hex}{ext}`; в БД —
   относительный путь (`devices/3/ab12….jpg`), URL собирается как
   `/media/{path}`. Оригинал пересохраняется Pillow без EXIF (avoids
   `exif_transpose`-зависимости и вычищает GPS-теги, F2); превью — `thumbnail`
   до 400 px по ширине. Альтернатива: хранить absolut пути — отклонена,
   ломает перенос `data/` при бэкапе.

5. **Запись файлов до коммита, компенсация при ошибке**: сервис сначала
   пишет файлы, затем строку + событие и коммитит; при любом исключении
   уже записанные файлы удаляются (`try/except` + unlink). Файлы не живут в
   БД, поэтому «файл без строки» — единственный возможный рассинхрон, и он
   убирается компенсацией. Идемпотентность удаления: `unlink(missing_ok=True)`.

6. **Раздача `/media/*` через `StaticFiles`-mount в `create_app()`** с
   `html=False`. Авторизация не проверяется (решение принято при уточнении):
   `OriginCheckMiddleware` трогает только мутирующие методы, GET отдаётся как
   есть. Каталог создаётся при старте (`mkdir(parents=True, exist_ok=True)`).

7. **Права**: чтение списка — любая сессия (`get_current_user`, как везде);
   загрузка — `ensure_can_act_on_hold` (владелец/держатель/admin) +
   запрет архива (`DEVICE_ARCHIVED`, 409); удаление — автор записи, владелец
   устройства или admin, иначе `FORBIDDEN` 403. Архивное устройство
   read-only и для удаления — 409 `DEVICE_ARCHIVED`.

8. **Фото в ответе отчёта**: `ConditionReportRead.photos: list[PhotoRead]`.
   Сериализатор `maintenance._report_list` дёргает один запрос
   `WHERE device_id = ...` и раздаёт фото по `report_id` — без N+1.

9. **Настройка `media_dir`**: свойство в `Settings` — `data_dir / "media"`;
   в `tests/conftest.py` до импорта приложения выставляется `DATA_DIR` во
   временный каталог, чтобы тесты не писали в рабочий `data/`.

## Risks / Trade-offs

- [Файл записан, коммит упал] → компенсирующее удаление файлов в `except`;
  тест на ошибку БД не пишем (искусственно), но порядок операций фиксирует
  код-ревью.
- [Pillow декомпрессионные бомбы] → лимит 10 МБ читается до `verify()`,
  превью считается с `Image.draft`/уменьшением — для внутреннего инструмента
  на 300 устройств достаточно.
- [`/media` без сессии] → файлы доступны любому, кто знает URL (принято
  пользователем: LAN, внутренний инструмент); имена — `uuid4`, что исключает
  перебор.
- [Лимит 5 считается до записи всех файлов] → гонка двух одновременных
  загрузок может дать 6 строк; частичный unique-index не делаем (избыточно
  для одного процесса), риск принят.
