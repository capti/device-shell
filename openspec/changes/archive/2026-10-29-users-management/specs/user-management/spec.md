# Spec Delta

## ADDED Requirements

### Requirement: Редактирование сотрудника

Admin SHALL изменять ФИО, контакты и роль существующего сотрудника; логин
после создания MUST NOT меняться.

#### Scenario: Админ правит карточку сотрудника
- **WHEN** admin отправляет новое ФИО, email, команду или Telegram
- **THEN** система сохраняет изменения и возвращает обновлённую карточку

#### Scenario: Админ меняет роль
- **WHEN** admin меняет роль `user` на `admin` или обратно
- **THEN** новая роль применяется к следующим запросам сотрудника

#### Scenario: Попытка изменить логин
- **WHEN** запрос на редактирование содержит `username`
- **THEN** система отвечает 422 и не меняет карточку

#### Scenario: Обычный пользователь правит сотрудника
- **WHEN** user отправляет `PATCH /users/{id}`
- **THEN** система отвечает 403

#### Scenario: Разжалование последнего админа
- **WHEN** admin меняет роль последнего активного admin на `user`
- **THEN** система отвечает 409 `LAST_ADMIN` и сохраняет роль

#### Scenario: Неизвестный сотрудник
- **WHEN** admin правит пользователя с несуществующим идентификатором
- **THEN** система отвечает 404 `USER_NOT_FOUND`

### Requirement: Сброс пароля администратором

Admin SHALL устанавливать сотруднику новый пароль без подтверждения старого;
пароль короче 8 символов MUST отклоняться.

#### Scenario: Админ сбрасывает пароль
- **WHEN** admin отправляет новый пароль от 8 символов
- **THEN** система сохраняет новый хеш, и сотрудник входит с новым паролем

#### Scenario: Слишком короткий пароль
- **WHEN** admin отправляет пароль короче 8 символов
- **THEN** система отвечает 422 `WEAK_PASSWORD` и не меняет пароль

#### Scenario: Обычный пользователь сбрасывает чужой пароль
- **WHEN** user вызывает сброс пароля другого сотрудника
- **THEN** система отвечает 403

#### Scenario: Сброс пароля неизвестному сотруднику
- **WHEN** admin сбрасывает пароль несуществующего пользователя
- **THEN** система отвечает 404 `USER_NOT_FOUND`

## MODIFIED Requirements

### Requirement: Деактивация пользователя

Деактивация SHALL архивировать все устройства пользователя, кроме уже
архивных, и закрывать ему доступ к системе.

#### Scenario: Деактивация владельца устройств
- **WHEN** admin деактивирует пользователя без активных выдач
- **THEN** все его устройства архивируются, доступ к системе закрывается

#### Scenario: Устройства в архиве и в ремонте
- **WHEN** admin деактивирует владельца, у которого часть устройств уже в
  архиве, а часть в статусе `repair` или `lost`
- **THEN** архивные остаются как были, остальные получают `archived_at`, статус
  не меняется, по каждому пишется событие `archived`

### Requirement: Блокировка деактивации при обороте

Деактивация MUST отклоняться, если у пользователя на руках чужие устройства или
у его устройств есть активные выдачи.

#### Scenario: Деактивация держателя
- **WHEN** admin пытается деактивировать пользователя, у которого на руках чужой телефон
- **THEN** система отвечает 409 и возвращает список проблемных устройств

#### Scenario: Деактивация владельца выданного устройства
- **WHEN** admin деактивирует владельца, чьё устройство сейчас у другого сотрудника
- **THEN** система отвечает 409 `HAS_DEVICES` и перечисляет инвентарные номера
  проблемных устройств

#### Scenario: Повторная деактивация
- **WHEN** admin деактивирует уже деактивированного пользователя
- **THEN** система отвечает 409 `ALREADY_INACTIVE` и ничего не меняет

#### Scenario: Деактивация последнего админа
- **WHEN** admin пытается деактивировать последнего активного admin
- **THEN** система отвечает 409 `LAST_ADMIN` и оставляет доступ

### Requirement: Скрытие деактивированных из выбора

Деактивированные пользователи MUST NOT предлагаться как владелец или держатель.

#### Scenario: Выбор владельца
- **WHEN** пользователь выбирает владельца устройства
- **THEN** в списке только активные сотрудники

#### Scenario: Список по умолчанию
- **WHEN** клиент запрашивает `GET /users` без параметров
- **THEN** ответ содержит только активных сотрудников

#### Scenario: Админский справочник с деактивированными
- **WHEN** admin запрашивает `GET /users?include_inactive=true`
- **THEN** ответ содержит и активных, и деактивированных сотрудников

#### Scenario: Назначение деактивированного
- **WHEN** запрос пытается сделать деактивированного владельцем или держателем
- **THEN** система отвечает 422 и не сохраняет изменение

### Requirement: Список сотрудников

Список SHALL отдавать каждого сотрудника со счётчиками устройств во владении
(включая архивные) и устройств, которые сейчас на руках (активные выдачи).

#### Scenario: Сводка по сотруднику
- **WHEN** admin открывает список сотрудников
- **THEN** напротив каждого видны счётчики «владеет» и «на руках»

#### Scenario: Архивные устройства в счётчике владения
- **WHEN** у сотрудника два устройства, одно из которых в архиве
- **THEN** счётчик «владеет» равен двум

#### Scenario: Чужое устройство на руках
- **WHEN** сотрудник держит телефон коллеги по активной выдаче
- **THEN** счётчик «на руках» учитывает это устройство, а «владеет» — нет

#### Scenario: Карточка сотрудника
- **WHEN** пользователь открывает `GET /users/{id}`
- **THEN** он видит профиль, роль, признак активности и те же счётчики

#### Scenario: Неизвестный сотрудник в карточке
- **WHEN** клиент запрашивает карточку несуществующего пользователя
- **THEN** система отвечает 404 `USER_NOT_FOUND`
