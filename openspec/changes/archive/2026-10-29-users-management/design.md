# Design

## Context

- Модель `User` уже содержит `username` (UNIQUE), `password_hash`, `full_name`,
  `email`, `team`, `telegram`, `role`, `is_active`, `created_at`,
  `last_login_at`. Миграции не нужны.
- `services/users.py` умеет только `get_user_by_username` и `create_user`
  (проверки логина, ФИО, длины пароля, роли и дубликата username).
- `get_current_user` уже отклоняет запросы деактивированного пользователя
  (`401 USER_INACTIVE`), поэтому закрытие доступа не требует удаления сессий.
- `ensure_can_manage`, `active_checkout`, `device_state_query`, `record_event`
  и `now_local` — готовые точки для автоархива и счётчиков.
- Ошибки — `AppError(code, message, status)` и конверт `{code, message}`;
  расширять конверт нельзя без изменения `api-errors`.
- `devices.py` отдаёт список устройств с фильтрами `owner_id`/`holder_id`,
  поэтому карточка сотрудника не дублирует список устройств.

## Goals / Non-Goals

**Goals:**

- Справочник сотрудников как отдельный ресурс `/users` с тонкими роутами и
  бизнес-логикой в сервисе.
- Один источник счётчиков и одно место проверки «последний админ».
- Деактивация — одна транзакция: проверки → архив устройств с событиями →
  `is_active = False`.
- Пароли: только argon2-хеш, длина проверяется в сервисе, сырой пароль нигде
  не логируется и не возвращается.

**Non-Goals:**

- Уведомления (B6), дашборд и Excel (B7), фото (B8), глобальный аудит (B9).
- Отзыв сессий, «выйти на всех устройствах», массовое переназначение устройств.
- Пагинация и полнотекстовый поиск по справочнику: команда небольшая, список
  отдаётся целиком.
- Изменение схемы БД и миграции.

## Decisions

### 1. Ресурс `/users` и матрица прав

| Метод | Путь | Кто | Назначение |
|---|---|---|---|
| `GET` | `/users` | любой авторизованный | список с счётчиками |
| `GET` | `/users/{id}` | любой авторизованный | карточка с счётчиками |
| `POST` | `/users` | admin | создание |
| `PATCH` | `/users/{id}` | admin | ФИО, контакты, роль |
| `POST` | `/users/{id}/deactivate` | admin | деактивация + автоархив |
| `POST` | `/users/{id}/activate` | admin | возврат доступа |
| `POST` | `/users/{id}/password` | admin | сброс пароля |
| `DELETE` | `/users/{id}` | любой авторизованный | всегда `405` |

Чтение открыто всем, потому что роли `viewer` в проекте нет и справочник нужен
для выбора владельца/держателя и страницы «Люди». Мутации — только admin
(`require_admin`), иначе `403 FORBIDDEN`.

Альтернатива — `PATCH` с полем `is_active`: отклонена, потому что деактивация
имеет отдельные проверки и побочные эффекты (автоархив), а смешивание с
обычной правкой усложняет порядок ошибок и тесты.

### 2. Счётчики — один агрегирующий запрос

`GET /users` строит `User` + два `LEFT JOIN` по подзапросам:

- `owned` — `COUNT(devices.id)` по `owner_id`, **включая архивные**:
  инвариант 7 говорит, что архивное устройство остаётся за владельцем;
- `held` — `COUNT(checkouts.id)` по `user_id`, где `returned_at IS NULL`
  (активная выдача).

Счётчики не зависят от просрочки и не пересчитываются на фронте. Карточка
`GET /users/{id}` использует те же два подзапроса для одного пользователя,
поэтому список и карточка не расходятся.

Список по умолчанию отдаёт только `is_active = true`, чтобы селекторы
владельца и держателя не показывали уволенных. `include_inactive=true`
включает всех — для админского справочника. Деактивированный пользователь
по-прежнему доступен по `GET /users/{id}` для истории.

Сортировка — `full_name`, затем `id`, стабильная без пагинации.

### 3. Правка сотрудника

`PATCH /users/{id}` разрешает `full_name`, `email`, `team`, `telegram`,
`role`; `extra="forbid"` превращает `username` и любые лишние поля в `422`.
Логин — идентификатор входа и внешних ссылок, поэтому не меняется.

Проверки: пользователь существует (`404 USER_NOT_FOUND`), ФИО не пустое
(`422 VALIDATION_ERROR`), роль из `admin|user` (Pydantic), разжалование
последнего активного admin — `409 LAST_ADMIN`. Пустые строки контактов
нормализуются в `NULL` тем же валидатором, что в схемах устройств.

### 4. Деактивация

Порядок проверок задаёт коды ошибок:

1. пользователь не найден — `404 USER_NOT_FOUND`;
2. уже неактивен — `409 ALREADY_INACTIVE`;
3. это последний активный admin — `409 LAST_ADMIN`;
4. есть устройства в обороте — `409 HAS_DEVICES`;
5. иначе — архив и деактивация.

«Устройства в обороте» — объединение двух множеств по активным выдачам:
`Device.owner_id = target.id` (его телефон у кого-то) и
`Checkout.user_id = target.id` (у него чужой телефон). При `holder != owner`
это разные устройства, поэтому нужны оба условия. Сообщение содержит
инвентарные номера: `Сначала верните устройства: QA-PH-001, QA-PH-002`.
Конверт ошибки остаётся `{code, message}` — список передаётся в `message`,
чтобы не менять `api-errors`.

Автоархив: для каждого неархивного устройства владельца выставляется
`archived_at = now_local()`, статус не меняется (устройство может быть
`repair`/`lost`), пишется событие `archived` с
`payload = {"reason": "owner_deactivated"}` и `actor_id` администратора.
Затем `is_active = False`; всё в одной транзакции (`audit-log`). Активных
выдач на этом шаге уже нет по проверке 4, поэтому инвариант 5 не нарушается.

Повторная активация (`POST /activate`) — `is_active = True`; устройства из
архива не возвращаются (инвариант 8). На уже активном пользователе —
`409 ALREADY_ACTIVE`.

### 5. Защита последнего администратора — одна функция

`_ensure_not_last_admin(db, user)` считает
`COUNT(*) FROM users WHERE role='admin' AND is_active=1`. Функция вызывается
и в `PATCH` (при смене роли admin → user), и в `deactivate`. Это единственное
место, где живёт правило «последнего admin нельзя разжаловать или
деактивировать».

### 6. Пароли

- `POST /users/{id}/password`, тело `{"password": "..."}`: admin, длина от 8
  символов (`422 WEAK_PASSWORD`), сохраняется `hash_password`, ответ `204`.
  Старый пароль не требуется: это сценарий «забыл пароль».
- `POST /auth/change-password`, тело `{"current_password": "...",
  "new_password": "..."}`: любой авторизованный; неверный текущий —
  `422 INVALID_PASSWORD`, короткий новый — `422 WEAK_PASSWORD`, успех —
  `204`. Требование `access-control` уже существует, endpoint добавляется
  здесь, потому что меняется та же логика паролей.
- Сессии не отзываются: отзыв при смене пароля отложен (решение 19 PLAN.md).
  Деактивированный пользователь теряет доступ через проверку `is_active` в
  `get_current_user`.

### 7. Схемы и ответы

`app/schemas/users.py`:

- `UserCreate` — `username`, `full_name`, `password`, `role = "user"`,
  `email/team/telegram = None`; `extra="forbid"`.
- `UserUpdate` — `full_name`, контакты, `role`; неприсланные поля не
  меняются, пустой контакт нормализуется в `NULL`, пустое ФИО — `422`.
- `PasswordReset`, `PasswordChange`.
- `UserRead` — профиль без `password_hash` + `devices_owned`,
  `devices_held`.

Ответы мутаций — `UserRead`, чтобы фронт сразу видел новые счётчики и
признак активности. Создание возвращает `201`, деактивация/активация/правка —
`200`.

### 8. Тестируемость

HTTP-тесты с реальными сессиями и `TestClient`:
чтение списка и карточки, скрытие деактивированных и `include_inactive`,
счётчики с архивным устройством и чужой выдачей, все мутации и `403` для
`user`, `404`, `USERNAME_TAKEN`, неизменяемость логина, `LAST_ADMIN` при
разжаловании и деактивации, `HAS_DEVICES` для обоих случаев оборота,
автоархив с событиями `archived`, активация без восстановления устройств,
`405` на `DELETE`, сброс и смена пароля (успех, короткий, неверный текущий).
Сервисные тесты в `test_users.py` дополняются проверкой счётчиков и
идемпотентности.

## Risks / Trade-offs

- **`GET /users` без пагинации** → при росте команды список станет тяжёлым;
  пока сотрудников десятки, это дешевле, чем пагинация в UI. Добавить
  параметры можно без ломающих изменений.
- **Счётчик владения включает архив** → «владеет» не совпадает с числом
  строк на странице устройств по умолчанию (там архив скрыт). Осознанно:
  архивное устройство всё ещё закреплено за человеком; в UI счётчик можно
  подписать.
- **Деактивация не отзывает сессии** → украденная cookie деактивированного
  пользователя перестаёт работать только из-за `is_active`; полноценный
  отзыв — отдельное отложенное изменение.
- **Список проблемных устройств в `message`** → фронт не получает
  структурированный массив. Компенсация: инвентарные номера однозначны и
  сразу ведут к карточкам; менять конверт ошибок ради этого не требуется.
- **Само-деактивация админа не запрещена отдельно** → при наличии второго
  админа он может закрыть себе доступ. Защищён только последний admin;
  отдельное правило добавило бы поведение, которого нет в спеках.

## Migration Plan

Миграций нет. Перезапуск backend и `uv run python -m app.export_openapi`.
Откат — revert коммита; данные и схема не меняются.
