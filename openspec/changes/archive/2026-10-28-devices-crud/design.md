# Design

## Context

См. `proposal.md` — Why. Что уже есть и важно для решений:

- Модели `Device`, `Checkout`, `DeviceEvent`, `User` описаны; partial unique
  index на активную выдачу и триггеры append-only уже в схеме. Миграция не
  нужна.
- `get_current_user` / `require_admin` в `app/api/deps.py`, ошибки —
  `AppError(code, message, status)` в `app/errors.py`.
- Тесты поднимают схему через `Base.metadata.create_all`; авторизация в тестах —
  реальный `POST /auth/login`.
- `device_events` пишется явно, без ORM-хуков; история append-only.

## Goals / Non-Goals

**Goals:**

- Один источник правды для `holder` и `overdue`: SQL-выражение, которое
  используют список и карточка, а позже — дашборд, фильтры и Excel.
- Права проверяются в сервисном слое, роуты остаются тонкими.
- Все мутации и событие истории коммитятся одной транзакцией.
- Поведение описано тестами через публичный HTTP API.

**Non-Goals:**

- Выдачи, передачи, смена владельца и смена статуса — отдельный change (B4).
- Кэширование, оптимизация под объёмы больше 300 устройств.
- Soft-delete и любые операции физического удаления.
- Изменения существующих таблиц и миграции.

## Decisions

### 1. Единое SQL-выражение состояния устройства

Новый модуль `app/services/device_state.py` строит `select` с `LEFT JOIN` на
активную выдачу (`Checkout.returned_at IS NULL`) и вычисляет:

```sql
holder_id  = COALESCE(checkout.user_id, devices.owner_id)
overdue    = checkout.id IS NOT NULL
             AND checkout.user_id <> devices.owner_id
             AND checkout.expected_return_at IS NOT NULL
             AND checkout.expected_return_at < date_start(today)
```

`date_start(today)` — полночь локального времени (`now_local().replace(...)`),
поэтому просрочка наступает в 00:00 (P1), а дата, равная сегодняшней, ещё не
просрочена.

Одна функция `device_state_query()` возвращает `(stmt, columns)`; список,
карточка и будущие отчёты берут состояние из неё. Дублировать формулу в
Python-схемах или на фронте нельзя — это прямо запрещено инвариантом 6.

Почему SQL, а не Python: фильтры `overdue`/`holder_id` и пагинация должны
считаться базой, иначе пришлось бы тянуть все строки и фильтровать в памяти.
`LEFT JOIN` безопасен: partial unique index гарантирует не более одной активной
выдачи.

### 2. Список: фильтры в SQL, счётчик по тем же условиям

`GET /devices` принимает:

- `q` — подстрока без учёта регистра по `inventory_no`, `serial_no`, `imei`,
  `model`, `brand`, а также по ФИО владельца и держателя (через `EXISTS`/join на
  `users`);
- `status` (`active|repair|lost`), `owner_id`, `holder_id`, `overdue`,
  `mine` (владею или держу), `archived` (`false` по умолчанию — только
  активные, `true` — только архивные, `all` — все);
- `sort` из белого списка (`inventory_no`, `model`, `updated_at`, с префиксом
  `-` для убывания), по умолчанию `inventory_no`;
- `page` ≥ 1 и `page_size` 1–100 (по умолчанию 25, H3), значения вне диапазона
  дают 422.

Ответ — `{items, total, page, page_size}`, где `total` считается тем же
`select` без `ORDER BY`/`LIMIT`. Фильтр `mine` = `owner_id = me OR
holder_id = me`.

### 3. Уникальность: предпроверка + гарантия БД

Сервис проверяет дубликаты запросом и отдаёт точный код:
`INVENTORY_TAKEN`, `IMEI_TAKEN`, `SERIAL_TAKEN` (409). Уникальные индексы в
БД остаются последней линией защиты: `IntegrityError` перехватывается и
превращается в `409 CONFLICT` с общим сообщением о дубликате.

Альтернатива — разбирать текст `IntegrityError` — отклонена: он зависит от
версии SQLite и легко ломается.

### 4. Автогенерация инвентарного номера

Если `inventory_no` пуст, берётся максимальный существующий номер вида
`QA-PH-NNN` (включая архивные), к нему прибавляется 1 и формат
нормализуется до трёх цифр (`QA-PH-1000` допустим). Номер генерируется под
записью в одной транзакции; при гонке сработает unique-индекс и клиент получит
409. Ручной номер сохраняется как есть после `strip()`.

### 5. Права и проверки в сервисе

`ensure_can_manage(device, user)`: `admin` — всегда, иначе только владелец.
Используется в `PATCH`, `archive`, `restore`. Создание: `user` не может указать
чужого владельца (403), отсутствующий владелец = сам создатель; `admin` может
указать любого **активного** пользователя (деактивированный → 422).

Восстановление устройства, чей владелец деактивирован, требует нового
активного владельца (422 без него). Целевой статус при восстановлении —
необязательный, по умолчанию `active`.

### 6. Архив и read-only

`archive`: `409 ACTIVE_CHECKOUT` при активной выдаче (и для admin), `409
ALREADY_ARCHIVED` при повторной архивации, событие `archived`.
`restore`: `409 NOT_ARCHIVED` для активного устройства, событие `restored`.
`PATCH` архивного устройства — `409 DEVICE_ARCHIVED` до восстановления.

`DELETE /devices/{id}` реализован явным роутом, который отвечает `405` с
сообщением «Удаление не поддерживается. Отправьте устройство в архив»: иначе
клиент получил бы обезличенное «Метод не поддерживается».

### 7. События истории в той же транзакции

Помощник `record_event(db, device_id, actor_id, type, payload)` добавляет
`DeviceEvent` без коммита; сервис коммитит устройство и событие вместе. Если
событие не записалось — откатывается вся операция (требование `audit-log`).
Payload фиксирует только изменённые поля, чтобы таймлайн был читаемым.

`GET /devices/{id}/history` отдаёт события в обратном хронологическом порядке
(сначала новые), с автором и payload. Выдач и отчётов в истории пока нет — они
появятся вместе с B4, формат ответа расширяется без ломки.

### 8. Pydantic-схемы закрыты для лишних полей

`model_config = ConfigDict(extra="forbid")` у входных схем. Поэтому `status` в
`PATCH` даёт 422, а не молча игнорируется: смена статуса — отдельная операция
B4 со своей проверкой прав. Пустые строки нормализуются в `None` для
необязательных полей, обязательные (`brand`, `model`) проверяются на непустоту.

### 9. Тестируемость

`device_state_query()` — единственное место, где вычисляются `holder` и
`overdue`; остальное проверяется через `TestClient` с реальными cookie-сессиями. Для списка
отдельные тесты на каждый фильтр, сортировку, `total` и на то, что архивные не
попадают в список по умолчанию. Тест «просрочка не ставится владельцу»
готовится вставкой активной выдачи напрямую в БД, потому что ручки выдачи ещё
нет.

## Risks / Trade-offs

- **Формула `overdue` продублируется в B4 при возврате/передаче** → B4 обязан
  импортировать `device_state`, а не писать своё условие; тест на список
  останется общим.
- **Поиск по ФИО через join может замедлиться** → 300 устройств и 50
  пользователей (N3), индексы по `owner_id` есть; при росте — FTS.
- **Автогенерация номера при гонке** → unique-индекс + 409; фронт покажет
  сообщение и предложит повторить.
- **`PATCH` не принимает `status`** → фронт B4 будет вызывать отдельную ручку;
  до неё статус меняется только через восстановление из архива.
- **История пока содержит только события карточки** → формат ответа —
  список событий, поэтому добавление выдач и отчётов не потребует миграции
  клиента.

## Migration Plan

Миграций нет. Достаточно перезапустить backend и перегенерировать
`backend/openapi.json`. Откат — revert коммита; данные и схема не меняются.
